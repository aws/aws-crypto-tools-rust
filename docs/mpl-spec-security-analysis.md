| # | Finding | Evidence | Impact |

| N1 | **Stale in-flight mark is never cleared on the error path.** A leader that never calls `put` (key store error, or the caller cancelled the future) leaves the key in flight. After `in_flight_ttl` (default 10 s) every miss for that key returns `Throttling` at classification. The same-key prune in `state_locked` keeps the caller's own key, so the mark persists until another key's call prunes it or a `put` happens. A single-key, low-traffic, encrypt-only service can stay wedged. The spec's "time spent so far exceeds the Inflight TTL" does not say who clears the mark | `cmc/storm_tracking.rs:249-258` (prune keeps `skip_key`), `:322-323` (error, entry untouched); test `test_get_miss_inflight_exceeds_ttl_fails` `mpl/tests/test_storm_tracking_cmc.rs:761-781` asserts the error, not recovery | Availability. Needs a reproducer before it is called a bug |
| N2 | **A cache-miss waiter with the fan-out saturated has no deadline.** `GetDecision::Wait { deadline: None }` skips the per-waiter timeout in `wait_for_leader`; the wait ends only when a slot frees (prune after `in_flight_ttl`, or a `put`). Spec "FanOut" says blocked requests also stop when the request has been outstanding longer than the Inflight TTL | `storm_tracking.rs:310-314`, `:360-398` | Availability |
| N3 | **Fan-out can be saturated from the decrypt input.** OnDecrypt filters EDKs only on provider id and branch key id (`hierarchical_keyring.rs:752-763`); the 16-byte version is read from the ciphertext (`:889-894`). Public API shape (current):
- Components are built with SDK-style builders. Required fields go through `required()` (`mpl/src/builder.rs:7`), setters append one item at a time (`grant_tokens`, `encrypted_data_keys`, required EC keys), `set_*` takes an `Option`, `get_*` returns `&Option<_>`. Validation happens in `build()`.
- Each operation is called on a handle as a fluent builder ending in `send()`. Trait implementors write the trait. Callers only see the fluent method (`mpl/src/shared.rs:12-16`).
- Smithy-conformant shapes: `*Input`/`*Output` with builders (`keyring/types.rs`, `cmm/types.rs`, `key_store/shapes.rs`, `cmc/operation.rs`). `key_store::operation::<op>::builders` mirrors the AWS SDK layout (`key_store/mod.rs:64-165`; the first pass said `:64-169`).
- Five pluggable traits are public, each `Send + Sync` and written with `#[async_trait]` (re-exported, `lib.rs:20`): `Keyring` (`keyring/mod.rs:150`), `Cmm` (`cmm/mod.rs:33`), `Cmc` (`cmc/mod.rs:46`, plus the default-`None` hook `grace_period`, `:88-90`), `KeyStore` (`key_store/mod.rs:172`) and `BranchKeyIdSupplier` (`aws_kms/hierarchical_keyring.rs:187`). Each has a `Shared*` handle from one macro (`shared.rs:62-104`). `impl FromUnshared<T: Trait> for Shared*` lets any user type become a handle; built-ins convert through their own `FromUnshared` impls that wrap them in `Builtin<T>` (`keyring/fluent_builders.rs:184-189`, `cmm/fluent_builders.rs:340-344`, `cmc/fluent_builders.rs:297-301`, `key_store/client_impl.rs:468-473`).
- Public shapes a pluggable component can build or read: `BranchKeyMaterials` (builder takes `[u8; 32]`; getter returns `&[u8; 32]`, `structures/branch_key_materials.rs:32`, `:79`), `CacheEntry`, `CachedMaterials` (`types.rs:6`). - Errors: one `Error` with a `Kind` (`error.rs`, `error/generated.rs`), SDK classification through the public `Error::from_sdk` (`error.rs`), aggregation with `Error::all_failed` / `any_failed`. `NoMatchingDataKey` carries `DataKeyInfo` (second pass N7).

| Suite KDF | HKDF-SHA256/384/512 or identity, per suite | n/a | MPL exposes the parameters. Message-level derivation belongs to the ESDK |

The suite table (`structures/algorithm_suite.rs`) covers the 11 ESDK suites. All use AES-GCM with a 12-byte IV and 16-byte tag. The commit-key suites (`04 78`, `05 78`) use HKDF-SHA512. DBE and S3EC suites are intentionally not implemented.

## Key Hierarchy

1. AWS KMS key: the root of trust; it never leaves KMS.
2. Branch key: 32 bytes from KMS `GenerateDataKeyWithoutPlaintext`, stored wrapped in DynamoDB and bound to an authenticated EC. That EC holds `branch-key-id`, `type`, `version`, `create-time`, `kms-arn`, `hierarchy-version`, `tablename` = logical key store name, and `aws-crypto-ec:*` custom pairs. Records: ACTIVE, one `branch:version:<v>` per version, and a beacon record. In memory it is `BranchKeyMaterials`, zeroized on drop, including every cache clone.
3. `derivedBranchKey`: 32 bytes from KBKDF(branch key, 16-byte random salt), one per wrap or unwrap. It is never stored and is wiped on drop.
4. Plaintext data key: random per message (or supplied by the caller), wrapped by `derivedBranchKey` or the raw AES wrapping key. `PlaintextDataKey` is zeroized on drop.

Rotation guidance (spec Appendix B) is unchanged: the 16-byte salt keeps AES-GCM key/IV reuse negligible, and annual rotation is recommended.

## Trust Boundaries

| Boundary | From | To | Data crossing |
|---|---|---|---|
| Client → CMM/keyring | Untrusted request, or message fields parsed by the ESDK | In-process MPL | EC, suite id, commitment policy, reproduced EC, EDK list (count, provider id, info and ciphertext all attacker-controlled on decrypt), caller PDK |
| MPL → user-supplied components (new) | MPL | User `Keyring`, `Cmm`, `Cmc`, `KeyStore`, `BranchKeyIdSupplier` | Materials, cache ids and entries, branch key ids. Keyring and CMM output is checked by `send()`. Key store, cache and supplier output is not |
| MPL → AWS KMS | In-process | KMS | Wrapped blob, EC as AAD, grant tokens, key ARN, user agent. Plaintext branch key comes back |
| MPL → DynamoDB | In-process | DDB | Branch-key items (attributes + `enc`). Records come back (tamper-evident only through the KMS AAD) |
| Keyring ↔ cache | In-process | In-process, possibly shared across keyrings | `BranchKeyMaterials` (plaintext 32-byte key) for the TTL. Cache-id domain separation is the isolation control |
| MPL → `prim` → aws-lc | Safe Rust | FFI (aws-lc-sys or FIPS) | Keys, plaintexts, IVs, AAD |
| C++ → shim → MPL (new) | C++ caller | Rust | Raw handle pointers (null-checked, `unsafe` deref at `esdk/shims/aws-esdk-cpp/src/lib.rs:720-728`; a non-null dangling pointer cannot be detected), optional KMS/DDB clients and cache (`:1570-1571`, `:1661`; null means "not supplied"). Caller retry config now also reaches DynamoDB (`:1411-1419`, second pass N9) |
| Test harness → MPL | Loopback HTTP client | `mpl/test-server` etc. | CBOR requests that build keyrings (including a raw wrapping key) and call the MPL. `127.0.0.1` only, no authentication (second pass N8). Not a production boundary |
| Message holder → decrypt path | Anyone who can submit ciphertext | Key store / DDB / KMS cost and storm-tracking slots | Attacker-chosen branch key versions drive cache misses and key store reads (second pass N3). Provider id and info echo into errors (N7) |

The most security-relevant boundary is still the keyring ↔ cache one. The cache may be shared, and with #4 it may now be a user implementation. Isolation then depends on (a) partition id and logical key store name in the cache id, and (b) the cache returning only what was put under that id. Only the material kind is checked (`as_branch_key_materials`, `hierarchical_keyring.rs:1000`). A user cache also receives the plaintext branch key in every `put_cache_entry` (`BranchKeyMaterials::branch_key`, `branch_key_materials.rs:32`), so a cache that persists or transmits entries moves the key outside the process.

## Data Flows

Encrypt (ESDK → DefaultCmm → hierarchical):
1. The ESDK calls `SharedCmm::get_encryption_materials().…send()` (`esdk/src/materials.rs:166`).
2. The CMM resolves the suite: the policy default (`commitment_policy.rs:43`), or the request's suite checked with `allows_for_encrypt` (`default_cmm.rs:97`). It refuses an EC that already holds `aws-crypto-public-key` (`:113`). For signing suites it generates an ECDSA key pair (`:137-138`, `.expect`) and inserts the base64 public key.
3. Empty `EncryptionMaterials` are built (RECK ⊆ EC enforced) and passed to `SharedKeyring::on_encrypt().send()` (`:166-171`).
4. Keyring: resolves the bkid (static or supplier with the EC), generates a PDK if none is present (`hierarchical_keyring.rs:975`), computes the encrypt-scope cache id (`:665`) and gets an entry from the cache. It uses the entry if `elapsed ≤ ttl` (`:989`). Otherwise it calls `get_active_branch_key` (`:692`), puts `expiry = now + ttl` (`:702`, BUG-01) and wraps.
5. Wrap: fresh salt and IV → KBKDF → AES-256-GCM with AAD built from **bkm's** bkid and version plus the EC. EDK = { `"aws-kms-hierarchy"`, provider info = **resolved** bkid (`:722`), ciphertext }.
6. `send()` runs `check_encryption_transition` (`fluent_builders.rs:82`). The CMM `send()` then runs `check_encryption_materials_complete` (`cmm/fluent_builders.rs:171`).

Decrypt:
1. The ESDK calls `SharedCmm::decrypt_materials().…send()` (`esdk/src/materials.rs:99`).
2. The CMM checks `allows_for_decrypt` (`default_cmm.rs:184`) and merges the reproduced EC (`:198`, `:273`). A mismatch is `EncryptionContextMismatch`. Reproduced-only keys are appended and become RECK. For signing suites it decodes the verification key from the merged EC. For non-signing suites the reserved key is rejected (`:224`).
3. Keyring `on_decrypt` (`hierarchical_keyring.rs:734`) refuses materials that already hold a PDK. It skips EDKs whose provider id is not the hierarchy id, whose provider info is not UTF-8, or whose bkid differs from the resolved one (`:752-763`).
4. `try_decrypt_edk` (`:867`): needs ≥ 44 bytes (`:879`) and reads the version at offset 28. Decrypt-scope cache id (`:908`). On a miss: `get_branch_key_version` (`:934`), put (`:945`). `unwrap` needs ≥ 60 bytes (`branch_key_wrap.rs:236`), re-derives the key and rebuilds the AAD from bkm and the decryption EC.
   With `StormTrackingCmc` as the cache, `get_cache_entry` also marks the cache id in flight on a miss (`storm_tracking.rs:308-316`); the mark is cleared only by a `put` (`:710-727`) or by age (`:249-258`). A failed key store call leaves the mark in place (second pass N1, N3).
5. The first success adds the PDK (length checked). If nothing matched, `NoMatchingDataKey` carries the EDK list (`:784`). If attempts failed, `all_failed` aggregates (`:798`).
6. `check_decryption_transition` (`fluent_builders.rs:163`), then `check_decryption_materials_complete` (`cmm/fluent_builders.rs:319`).

Key store reads (`DynamoDbKeyStore`): GetItem by `(branch-key-id, type)` → `resolve_key_store_arn` (config-compatible ARN; Discovery uses the record ARN with alias rejected; MrDiscovery rewrites the region, BUG-04) → KMS Decrypt with the auth EC (record attributes + `tablename`) → `branch_key_materials_from_authenticated_encryption_context` (`record.rs:95`).

CreateKey / VersionKey: these need a single-key config (`branch_key_store.rs:112`). CreateKey writes DECRYPT_ONLY, ACTIVE (ReEncrypt from DECRYPT_ONLY) and beacon in one transaction with `attribute_not_exists`. VersionKey authenticates ACTIVE by ReEncrypt-to-self with the rebuilt EC (`InvalidCiphertextException` → `Cryptographic`). It then writes the new version and overwrites ACTIVE under `#enc = :encOld` (`:752`).

## Constraints and Trade-offs

- **Duvet gap unchanged.** There is no MPL Duvet config and one annotation in the whole crate, so all MUSTs above are traced by hand.
- **Materials checks cover only the fluent path.** Every built-in and ESDK path goes through `send()`. A user's own `Keyring`/`Cmm` called directly through its trait by the user's code skips the checks; that is the user's choice and does not cross an MPL boundary. The checks do not re-validate PDK length (the builder does) or bind EDK content to the keyring.
- **User key stores and caches are trusted.** `SharedKeyStore` and `SharedCmc` pass results through unchecked. A key store controls `logical_key_store_name` (cache-id separation) and the returned `BranchKeyMaterials` (bkid/version are not compared with the request). A cache controls which entry comes back for an id. Only the material kind is checked. Integrity of wrapped data keys still rests on the AAD binding, so lying here causes failures or wrong-key wraps, not silent plaintext disclosure, unless the attacker also controls the materials.
- **Storm-tracking config regression** (change #9). Bad settings (grace period 0, in-flight TTL > grace period) are accepted. The impact is availability and caching efficiency, not confidentiality. Also check that any verification target written against the old `from_raw` contract is updated. Re-confirmed in the second pass against the spec "Consistency" section and the tests (`mpl/tests/test_storm_tracking_cmc.rs:368-384`, `:388-404`).
- **Storm-tracking availability (second pass N1-N3, static reasoning).** A key left in flight by a leader that never `put`s stays marked; after `in_flight_ttl` every miss for it returns `Throttling` until another key's call prunes the mark. A waiter blocked behind a saturated fan-out has no deadline of its own. Attacker-chosen branch key versions in decrypt input can fill the fan-out. Cache hits are unaffected. Spec ambiguity (N11d) is part of the cause. A reproducer is needed before these are rated.
- **Cache grace-vs-TTL check depends on the cache reporting a grace period.** `Cmc::grace_period()` defaults to `None`; a user cache that refreshes early but does not override it is not checked (`cmc/mod.rs:88-90`).
- **`SharedCmm` does not re-check policy-level output** (N4). The ESDK does (`esdk/src/materials.rs:130`, `:202`). Another MPL consumer with a user CMM has no backstop.
- **Error content** (N7). `NoMatchingDataKey` exposes provider id and info through `Debug` and `encrypted_data_keys()`; ciphertext is excluded (`prim/src/error.rs:378`). Treat provider info as attacker-supplied text when logging.
- **Test-server crates** (N8) bind loopback only and have no authentication; they must stay test-only. They are the repo's own `Keyring` and `BranchKeyIdSupplier` implementers.
- **C++ shim changes in this pass** (N9, N10): caller retry config now reaches DynamoDB; linking no longer depends on Cargo's build directory layout. Neither changes a trust boundary. The `unsafe` handle derefs moved to `:728`, `:1570-1571`, `:1661`.
- **Secret lifetime, improved but not total.** Still not zeroized: the `Vec<u8>` returned by `branch_key_wrap::unwrap` until it is wrapped in `PlaintextDataKey`; the raw AES decrypt buffer on the error and wrong-length paths (`raw_aes_keyring.rs:471`, `:489-495`); the KMS SDK response `Blob` before `Zeroizing` takes over (`kms_ops.rs:199-208`); and `Vec` reallocations. The cache holds plaintext branch keys for at least the TTL (by design) and can hold an expired entry longer, because `LocalCmc` drops expired entries only when it reads them, prunes `entry_pruning_tail_size` (default 1) LRU-tail entries per get, or evicts at capacity (`cmc/local.rs:69`, `:131-157`, `:166-182`; second pass C3). Entries are zeroized when dropped, not when they expire. A user `Cmc` receives the plaintext key in every `put_cache_entry`.
- **Panics remaining in non-test code**: `default_cmm.rs:123`, `:137-138` (BUG-05a); `user_agent.rs:17`; fixed-size `try_into().expect` (`branch_key_wrap.rs:249`, `:252`, `:256`, `hierarchical_keyring.rs:892`, unreachable after length checks); `cache_entry_identifier.rs:64`; `SystemTime + Duration` at `hierarchical_keyring.rs:702`, `:945`, `storm_tracking.rs:333`, `:680` (BUG-01, reachable with large configured durations).
- **Open bug locations**: BUG-04 `key_store/kms_ops.rs:100`, `:144`. BUG-05b `hierarchical_keyring.rs:879` vs `branch_key_wrap.rs:236`. BUG-06 `cache_entry_identifier.rs:42-61`. BUG-07a `prim/src/lib.rs:185-187` (plaintext copied into the output before key/nonce validation). BUG-07b `:215` vs `:228`. BUG-08 `key_store/encryption_context.rs:91`, `:95`.
- **Spec deviations** (documented in code unless noted): FORBID default suite (`commitment_policy.rs:46-48`); storm in-flight TTL default (`storm_tracking.rs:117-118`); hierarchical EDK provider info from the resolved bkid (`hierarchical_keyring.rs:722`; not documented in code); table-name length check (not in the spec, `branch_key_store.rs:384-388`); `aws_kms_mrk_match_for_decrypt` returns `false` for identical alias ARNs (`mrk_match.rs:12-28`, documented); DBE commitment policy and its default suite `67 01` are not implemented (`commitment_policy.rs:8-10`, documented); the grace-vs-TTL rule is applied to any cache that reports a grace period (`hierarchical_keyring.rs:584-593`); stricter-than-spec `aws-crypto-public-key` consistency in `materials_checks` (the spec says SHOULD; `structures.md` "Encryption Context", `cmm-interface.md`); **recorded by the Verus proofs (model level, not the shipped code):** O1 DEV-ALIAS (the identical-alias-ARN deviation above; confirmed by the T03 proof `verus-proofs/t03_resolve_pinned_arn.rs`, Proved (model level, not the shipped code, under stated hypotheses): 39 verified, 0 errors, which also shows it is unreachable for a configuration `build()` accepts); G1 (a branch-key record without `create-time` and `hierarchy-version` is accepted, see the MUST index row for "Record Format"; T02 proof) and O2 (the model of ARN validity accepts an ARN with empty partition, region and account, which `aws-kms-key-arn.md` does not allow; it does not affect the T03 property, and whether config validation should reject such ARNs is an owner decision; T03 proof).
- **Feature-dependent behavior**: verification must name the feature set. ESDK builds the MPL with `default-features = false` and re-enables features through its own (`esdk/Cargo.toml:19-20`, `:43-54`); the shim builds with defaults. Without `rt-tokio` there is no storm-tracking cache, no default cache and no grace-vs-TTL check; without `kms`+`ddb` there is no `DynamoDbKeyStore`. See [Cargo features and code paths](#cargo-features-and-code-paths).
- **CVE context (CVE-2026-6550 / GHSA-v638-38fc-rhfv, ESDK Python)**: a shared caching CMM served non-committing materials across commitment policies. This crate has no caching CMM (`mpl/src/cmm/` = `default_cmm.rs`, `fluent_builders.rs`, `mod.rs`, `types.rs`), but `CachedMaterials::Encryption`/`Decryption` exist (`cmc/entry.rs:26`, `:28`). A future caching CMM must bind the commitment policy (or suite) into its cache id. The hierarchical keyring caches only branch keys, which do not depend on the policy.
- **Spec silent / ambiguous areas**: what a keyring must verify about key store output; storm-tracking behavior with zero durations; whether `EncryptionContext::from_bytes` must reject empty keys (`test_deserialize_accepts_empty_key_length_currently_unenforced`, `mpl/tests/test_encryption_context.rs:468`); the on-wire branch-key version being authenticated only through AAD and KDF; the KDF fixed-info byte layout (F1: confirmed as a spec gap, not a code defect, by the T05 proof `verus-proofs/t05_kbkdf_fixed_info.rs`, Proved (model level, not the shipped code, under stated hypotheses): 33 verified, 0 errors, for `label ‖ 0x00 ‖ salt(16) ‖ 00 00 01 00`, 38 bytes, 32-byte output); the storm-tracking default Inflight TTL (20 s) contradicting its own ordering MUST with the default Grace Period (10 s); who clears a stale in-flight mark; what "configured Branch Key Identifier" means for a supplier; and whether a cache entry with a future creation time is fresh (N6).

## Concise Summary (for threat modeling and verification recommendation)

Key components: `prim` (crypto choke point), the shared-handle layer with materials checks, `RawAesKeyring`, `HierarchicalKeyring` + `branch_key_wrap`, `DefaultCmm`, `DynamoDbKeyStore` + `kms_ops`/`record`, and `LocalCmc`/`StormTrackingCmc`/`DefaultCmc`.

Trust boundaries: client → CMM (untrusted EC/suite/EDKs, now including EDK-count memory and attacker-chosen branch key versions), MPL → KMS/DDB, keyring ↔ cache (plaintext branch key for at least the TTL, possibly longer; shared or user-supplied), MPL → user components (new; only the keyring and CMM outputs are checked), C++ → shim (new, raw handles), and loopback test-server crates (test only).

Most security-critical invariants to verify:
1. Hierarchical AAD `"aws-kms-hierarchy" ‖ bkid ‖ version(16) ‖ EC` and KBKDF fixed info `label ‖ 0x00 ‖ salt ‖ 0x00000100`.
2. Key store auth-EC binding on every KMS call, 32-byte branch key, VersionKey authentication + optimistic lock, and ARN/MRK resolution (BUG-04 open).
3. Cache-id injectivity and domain separation (BUG-06 open), now also under user-supplied key stores and caches.
4. Materials transition checks: `send()` accepts a keyring result iff it only adds a PDK/EDKs. Commitment-policy gating, with the documented FORBID default deviation.
5. Storm-tracking config consistency (regressed) and the state machine.
6. Secret lifetime: zeroize-on-drop now covers PDK, signing keys, branch/beacon keys, wrapping keys and the derived key. Remaining gaps are listed above.
7. `prim` length checks and the absence of panics (BUG-01, BUG-05a, BUG-07).
8. Storm-tracking liveness (second pass N1-N3): in-flight marks are cleared only by `put` or age, a saturated-fan-out waiter has no deadline, and the spec does not say who clears a stale mark. State the property per feature set (`rt-tokio`).
9. The `Shared*` check matrix: which handle validates what (keyring in and out, CMM out only, cache/key store/supplier none), and what a user component can therefore get wrong without an MPL error.
10. Spec-vs-code deviations to carry into any proof: FORBID default `03 78`; storm-tracking ordering not enforced; MRK match alias rule; MRDiscovery rewrite of non-MRKs; resolved-bkid provider info; grace-vs-TTL generalized through `Cmc::grace_period`.
