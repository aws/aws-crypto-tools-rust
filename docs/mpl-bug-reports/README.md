# Bug reports: MPL native Rust

These ten reports came out of the Verus verification-target analysis of the AWS Cryptographic Material Providers Library (MPL) native Rust implementation (`docs/mpl-verification-targets.md`, `docs/mpl-verification-targets/01-threat-driven.md`, `docs/mpl-verification-targets/02-capability-driven.md`, `docs/mpl-threat-model.md`). Each one is a likely defect, or an observation that needs a decision, found while stating provable properties. BUG-01 to BUG-09 were first made and reproduced at commit `a1e23d7`. The reproducers were temporary, untracked tests. BUG-10 was added on 2026-11-17 from the `Mahnush_Verus` branch (tip `2d229377`, PR #103), where it was found by code reading while reviewing the mpl callers for BUG-07; it was re-found and checked on `MPL-Verus` by code reading. No code was changed for the original analysis, the re-check or BUG-10.

Re-check against `main`: on 2026-11-10, all nine findings that existed then (BUG-01 to BUG-09) were re-checked against `main` `620771c` (merged into `MPL-Verus` as `c256243`; the code is identical). The results are in [RECHECK-main-620771c.md](RECHECK-main-620771c.md). Where the public API had changed, the reproducers were adapted for API changes only, keeping the same inputs and observations. BUG-02, BUG-03 and BUG-09 are fixed on `main`, all in commit `e9bde48` (#98). The other six are still present. BUG-10 is still present on `main` by code reading (`mpl/` is identical to `620771c`). Each report now starts with a "Status on main (620771c)" block and cites current file:line locations. Reports of bugs that are still present keep their fix options and questions. Reports of fixed bugs keep the original analysis as history and end with a short "Resolved" note. Since then `main` moved from `620771c` to `5f2dc72` with esdk-only commits #188 and #189. `mpl/` and `prim/` are unchanged, so every status below still holds (proof in the addendum of the re-check report).

How to read the table:
- Severity, confidence and spec conflict are the values from the original analysis at `a1e23d7`. The re-check did not change them. The one exception is BUG-06: Severity raised Low -> High on the owner's decision after the main re-check. The BUG-06 report gives the basis (the end-to-end result on `main`, the non-injective cache identifier, and the High ratings of TM-MPL-009 and TM-MPL-010) and the preconditions: a `Shared` cache plus a NUL-containing partition ID, logical key store name or branch key ID, reachable through a caller-supplied value or a branch key ID supplier.
- Related threats: the IDs and ratings come from `docs/mpl-threat-model.md` (bug to threat table and Appendix: Threat Risk Matrix, second pass, TM-MPL-001..026). Related targets: the IDs come from `docs/mpl-verification-targets.md`. T27 (TM-MPL-025, provisional) was added at HEAD 9955ecd; T21 (i) is the property "no panic under the storm-tracking state lock". Both columns agree with the bug to threat to target mapping in `docs/mpl-completeness-audit.md` section 3b. BUG-10 is newer than section 3b and is not listed there; its IDs come from TM-MPL-015 and T26, which already name the site as a residual. Where a report also lists a threat that section 3b omits (TM-MPL-017 for BUG-03, TM-MPL-022 for BUG-01, TM-MPL-011 for BUG-07), the extra ID comes from the target's own threat references.
- Spec conflict "yes" for BUG-03, BUG-04 and BUG-06 depends on how the spec is read, or on text where the spec contradicts itself. Each report explains which.
- "Likely not a bug" means the behavior was reproduced but matches the Dafny MPL, or has no practical impact.
- Formal check: the BUG-08 report has a "Formal check (C01)" section. The C01 Verus proof (model level, not the shipped code) shows the collision branch is dead if and only if A_ITER holds. No status, severity, confidence or evidence of any bug changed.
- Formal check (T06): the BUG-01 report has a "Formal check (T06)" section. The T06 Verus proof (model level, not the shipped code; the platform range of `SystemTime` is assumed) shows that accepted configurations such as `Duration::MAX` make each of the four additions panic, and records four intentional expected-FAIL obligations. No status, severity, confidence or evidence of any bug changed.
- Formal check (T17): the BUG-04 report has a "Formal check (T17)" section. The T17 Verus proof (model level, not the shipped code) records one intentional expected-FAIL obligation: the claim that a non-MRK record comes back unchanged from MrDiscovery is false for the model, with the report's own ARN pair as the counterexample, and the failing set is exactly the non-MRK records whose region differs from the configured one. The shipped arm has no prefix test. No status, severity, confidence or evidence of any bug changed.
- Discussion priority is a suggested order (1 = first). It weighs spec deviation, cross-runtime divergence and impact, not just severity. The order was revised after the re-check. Open bugs come first, and fixed bugs move to the end. BUG-06 is at the top: with BUG-02 fixed, it is the open finding with the most direct impact, the re-check confirmed on `main` that keyring B was served keystore A's branch key, and its severity is now High. The remaining open bugs keep their original relative order (BUG-01, BUG-04, BUG-07, BUG-05, BUG-08), followed by the fixed bugs in their original order (BUG-02, BUG-03, BUG-09). BUG-10 is placed at 6, after the other Low open bugs and before the Informational BUG-08, because it is Low, rests on code reading only, and needs both an authenticating wrong-length EDK and access to process memory. Adding it moved BUG-08 and the fixed bugs down by one; no other relative order changed.
- Changes at HEAD 9955ecd to the priority column: the order is unchanged, because no cross-reference change justifies a move. TM-MPL-025 and T27 relate to BUG-05(b), but the threat model states that (b) is not their cause, so BUG-05 stays at 5. The BUG-06 label changed from "1 – Medium" to "1 – High" so that it matches its severity; the label words for the other rows are unchanged.
