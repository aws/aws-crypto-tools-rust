# Bug reports: MPL native Rust

These nine reports came out of the Verus verification-target analysis of the AWS Cryptographic Material Providers Library (MPL) native Rust implementation (`docs/verification-targets.md`, `docs/verification-targets/01-threat-driven.md`, `docs/verification-targets/02-capability-driven.md`, `docs/threat-model.md`). Each one is a likely defect, or an observation that needs a decision, found while stating provable properties. The findings were first made and reproduced at commit `a1e23d7`. The reproducers were temporary, untracked tests. No code was changed for either the original analysis or the re-check.

Re-check against `main`: on 2026-11-10, all nine findings were re-checked against `main` `620771c` (merged into `MPL-Verus` as `c256243`; the code is identical). The results are in [RECHECK-main-620771c.md](RECHECK-main-620771c.md). Where the public API had changed, the reproducers were adapted for API changes only, keeping the same inputs and observations. BUG-02, BUG-03 and BUG-09 are fixed on `main`, all in commit `e9bde48` (#98). The other six are still present. Each report now starts with a "Status on main (620771c)" block and cites current file:line locations. Reports of bugs that are still present keep their fix options and questions. Reports of fixed bugs keep the original analysis as history and end with a short "Resolved" note.

How to read the table:
- Severity, confidence and spec conflict are the values from the original analysis at `a1e23d7`. The re-check did not change them. BUG-06 carries a "Severity review suggested" note in its report. Its severity is unchanged.
- Spec conflict "yes" for BUG-03, BUG-04 and BUG-06 depends on how the spec is read, or on text where the spec contradicts itself. Each report explains which.
- "Likely not a bug" means the behavior was reproduced but matches the Dafny MPL, or has no practical impact.
- Discussion priority is a suggested order (1 = first). It weighs spec deviation, cross-runtime divergence and impact, not just severity. The order was revised after the re-check. Open bugs now come first, and fixed bugs move to the end. BUG-06 moves to the top: with BUG-02 fixed, it is the open finding with the most direct impact, and the re-check confirmed on `main` that keyring B was served keystore A's branch key. The remaining open bugs keep their original relative order (BUG-01, BUG-04, BUG-07, BUG-05, BUG-08), followed by the fixed bugs in their original order (BUG-02, BUG-03, BUG-09).
