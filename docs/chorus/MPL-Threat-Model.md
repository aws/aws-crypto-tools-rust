## 1. Executive summary

Scope. The review covers MPL key management in `mpl/` and the safe aws-lc-rs wrappers in `prim/`: keyrings, the default CMM, branch-key derivation and wrapping, the DynamoDB/KMS branch key store, KMS ARN and multi-Region key (MRK) matching, commitment policy, and the in-process caches. The ESDK message format is out of scope.

Headline numbers.

- 23 threats across all six STRIDE categories: Spoofing 3, Tampering 5, Repudiation 1, Information Disclosure 3, Denial of Service 3, Elevation of Privilege 8.
- Risk ratings: 1 High, 15 Medium, 7 Low.
- Severity ratings: 5 Critical, 9 High, 7 Medium, 2 Low.
- 21 of 23 threats have at least one Verus verification target; 2 (TM-MPL-019, TM-MPL-020) are not provable in code. The targets are recommendations; the sources report no completed proofs.
- 9 bug reports exist (BUG-01 to BUG-09); 7 of them link to one or more threats in this model. A re-check against `main` `620771c` (2026-11-10, `docs/bug-reports/RECHECK-main-620771c.md`) found BUG-02, BUG-03 and BUG-09 fixed on `main`; the other six are still present. Only the bug status was re-checked; the threats and ratings in this document were not.

Top risks.

- TM-MPL-005, branch-key record substitution: the only High-risk threat. It is mitigated by binding every record attribute into the KMS encryption context, so correctness depends on the reconstructed context matching the write-time context exactly.
- TM-MPL-011 and TM-MPL-012, AES-GCM IV and salt reuse: Critical severity. Uniqueness rests on CSPRNG randomness, not counters.
- TM-MPL-002, TM-MPL-004, TM-MPL-007, KMS key and ARN confusion: Critical/High severity. Pinned-ARN modes are mitigated; Discovery modes trust the record's ARN, and ARN parsing is unverified string handling.
- TM-MPL-006 and TM-MPL-008, commitment-policy bypass (Invisible Salamanders class): depends on the correctness of the per-suite allow tables.
- TM-MPL-010, shared-cache confusion: no check that a cached entry's commitment matches the current policy.
- TM-MPL-015, no zeroization of secret material: the largest code-level defense-in-depth gap.

## 2. Scope and assumptions

### 2.1 In scope

- `mpl/` key management: `RawAesKeyring`, `HierarchicalKeyring`, `branch_key_wrap`, `cache_entry_identifier`, `mrk_match`, `DefaultCmm`, commitment policy and algorithm suites, `BranchKeyStore`, `kms_ops`, `kms_config`, `record`, the local cache (`cmc/local`) and the storm-tracking cache (`cmc/storm_tracking`).
- `prim/` (`aws-mpl-primitives`): safe wrappers for AES-GCM, KBKDF, HKDF, HMAC, digest, ECDSA and the CSPRNG.
- Secret-material lifetime in process memory.
- The specification in `spec/framework/*.md` as the reference for intended behavior.

### 2.2 Out of scope

- ESDK message format: header and body serialization, framing, and message-level signature verification.
- The internals of AWS KMS, Amazon DynamoDB and aws-lc-rs, beyond the guarantees listed as assumptions.
- Application logging and the correctness of caller-supplied code such as a custom `BranchKeySupplier`.

### 2.3 Assumptions

- The process, the local AES wrapping key and the in-process cache are trusted.
- AWS KMS is the root of trust for branch and beacon keys and enforces the encryption context as AAD.
- DynamoDB is untrusted for integrity. Records are made tamper-evident by KMS encryption-context binding.
- Network traffic to KMS and DynamoDB uses TLS. Residual network threats are downgrade and denial of service.
- aws-lc-rs is reached only through the safe `prim` wrappers.
- Cryptographic primitives (AES-GCM, HMAC-SHA-256, SHA-384) are secure.
- Inline Duvet annotations are not present on this branch (they live on `duvet/mpl-annotations`). Mitigations cite code locations and spec sections directly. This gap is itself tracked as TM-MPL-019.

## 3. System overview

### 3.1 Components

| Component | Location | Role |
|---|---|---|
| DefaultCmm | `cmm/default_cmm.rs` | Resolves algorithm suite under the commitment policy, generates ECDSA keys for signing suites, merges reproduced encryption context on decrypt |
| RawAesKeyring | `keyring/raw_aes_keyring.rs` | Wraps data keys locally with AES-GCM under a long-lived wrapping key |
| HierarchicalKeyring | `aws_kms/hierarchical_keyring.rs` | Wraps data keys under KMS-protected branch keys, using the cache and the key store |
| branch_key_wrap | `aws_kms/branch_key_wrap.rs` | KBKDF derivation of a per-wrap key and AES-256-GCM wrap/unwrap with bound AAD |
| cache_entry_identifier | `aws_kms/cache_entry_identifier.rs` | SHA-384 cache identifier over scope, partition, logical name, branch key id and version |
| mrk_match | `aws_kms/mrk_match.rs` | MRK-aware ARN matching for decrypt |
| Cryptographic materials cache (Cmc) | `cmc/local.rs`, `cmc/storm_tracking.rs` | In-process cache of branch-key materials with TTL; storm tracking coalesces refreshes |
| BranchKeyStore | `keystore/branch_key_store.rs` | Reads and writes branch-key records in DynamoDB; creates and versions keys |
| kms_ops, kms_config, record | `keystore/` | KMS calls with authenticated encryption context, ARN validation, record-to-materials mapping |
| prim | `prim/src/lib.rs` | Only primitive crypto surface; safe wrappers over aws-lc-rs |

### 3.2 Architecture and data flow

```
                         Caller (ESDK / DB-ESDK / S3EC)
                                    |
                         get_encryption_materials / decrypt_materials
                                    v
                          +---------------------+
                          |   DefaultCmm        |  commitment-policy + suite
                          | (cmm/default_cmm)   |  resolution, ECDSA keygen,
                          +---------------------+  reproduced-EC merge
                                    |
                             on_encrypt / on_decrypt
                                    v
              +-----------------------------------------------+
              |                 Keyring                       |
              |  RawAesKeyring          HierarchicalKeyring   |
              +-----------------------------------------------+
                 |                        |            |
        AES-GCM (prim)          Cmc cache        Keystore (BranchKeyStore)
        local wrapping key      (Local/Storm)         |         |
                                    |            AWS KMS    Amazon DynamoDB
                                (in-process)   (wrap/unwrap) (branch-key records)
                                    |
                          branch_key_wrap (KBKDF + AES-GCM)
                                    |
                              prim (aws-lc-rs)
                          AES-GCM / KBKDF / HKDF / ECDSA / digest / RNG
                                    |
                              aws-lc-rs FFI (unsafe edge, reached only via safe prim)
```

Diagram in prose. A caller (ESDK, DB-ESDK or S3EC) asks the DefaultCmm for encryption or decryption materials. The CMM resolves the algorithm suite under the commitment policy, generates an ECDSA key pair for signing suites, and on decrypt merges the reproduced encryption context. It then calls a keyring's on_encrypt or on_decrypt. The RawAesKeyring wraps the data key directly with AES-GCM under a local wrapping key. The HierarchicalKeyring looks up branch-key materials in the in-process cache (local or storm-tracking). On a miss it asks the BranchKeyStore, which reads the record from DynamoDB and has AWS KMS decrypt it. The branch key is then used by branch_key_wrap, which derives a per-wrap key with KBKDF and wraps the data key with AES-256-GCM. All primitive cryptography goes through the prim crate, which is the only code that reaches the aws-lc-rs FFI.

Encrypt path (hierarchical keyring). The keyring resolves the branch key id and computes cache id = SHA-384(0x02, 0x01, partition, logical name, branch key id). On a cache miss it calls the key store for the active branch key (KMS Decrypt with the encryption context as AAD) and caches the result with a TTL. It then derives a key with KBKDF(salt) and seals the data key with AES-256-GCM, with AAD = label, branch key id, version, encryption context. The EDK has provider id `aws-kms-hierarchy`, provider info = branch key id, and ciphertext = salt, IV, version, encrypted key, tag.

Decrypt path (hierarchical keyring). The CMM checks that the suite is allowed for decrypt and merges the reproduced encryption context. The keyring filters EDKs by provider id and branch key id, parses the 16-byte version from ciphertext bytes 28 to 44, and computes cache id = SHA-384(0x02, 0x02, partition, logical name, branch key id, version). It obtains the branch-key materials from the cache or key store, derives the key with KBKDF(salt), and opens the AES-256-GCM ciphertext.

| ID | Boundary | What crosses | Controls |

### 4.2 Threat actors

Legitimate actors are the application caller, AWS KMS (root of trust), DynamoDB (storage), and operators who configure key stores and keyrings.

| ID | Actor | Capability |
|---|---|---|
| TA1 | DynamoDB tamperer | Read and write access to the branch-key table, but not to the KMS keys |
| TA2 | Malicious or confused caller | Controls encryption context, reproduced context, suite id and branch-key supplier; can submit crafted EDKs on decrypt |
| TA3 | Co-tenant on a shared cache | Shares a cache through a partition-id or logical-name collision |
| TA4 | In-process memory adversary | Reads freed heap, core dumps or swap (post-exploitation, cold boot) |
| TA5 | Network attacker between MPL and KMS/DynamoDB | TLS assumed; residual is downgrade and denial of service |
| TA6 | Supply-chain adversary | Targets aws-lc-rs, uuid, lru or AWS SDK dependencies |

## 6. Threat details

Each entry gives the attack, the existing mitigation as described in the source, and the residual risk. Ratings are in the register above.

### Spoofing

TM-MPL-001: Raw-AES key-provider-id impersonation.

- Attack: a caller sets the key namespace to `aws-kms` or `aws-kms-hierarchy` so its EDKs look like KMS-keyring EDKs.
- Mitigation: `RawAesKeyring::new` rejects any namespace equal to or starting with `aws-kms` (`raw_aes_keyring.rs`; spec raw-aes-keyring.md).
- Residual: the control is a prefix heuristic only.

TM-MPL-002: Branch-key record decrypts under an attacker-influenced KMS key.

- Attack: a DynamoDB tamperer (TA1) writes a record whose `kms-arn` points at an attacker-controlled key.
- Mitigation: for `KmsKeyArn` and `KmsMrKeyArn` configurations, `resolve_keystore_arn` sets the KMS KeyId to the configured ARN, so KMS decrypts under the trusted key (`kms_ops.rs`; spec branch-key-store.md).
- Residual: Discovery modes trust the ARN in the record.

TM-MPL-003: Malicious branch-key supplier.

- Attack: a caller-provided supplier returns an attacker-chosen branch key id.
- Mitigation: the supplier is caller-provided trusted code, and the chosen id is bound into the cache id and the AAD, so a wrong id fails authentication.
- Residual: none stated beyond the trust placed in caller code.

### Tampering

TM-MPL-004: Over-permissive ARN/MRK match.

- Attack: match logic accepts a key ARN that should not match.
- Mitigation: `aws_kms_mrk_match_for_decrypt` returns true only on exact equality or, for MRK ARNs, equality of partition, service, account id, resource type and resource with the region ignored. Aliases are rejected (`mrk_match.rs`; spec aws-kms-mrk-match-for-decrypt.md).
- Residual: ARN parsing uses ad-hoc string parsers; the source calls this a strong verification candidate.

TM-MPL-005: Branch-key record substitution.

- Attack: swap in a valid record from another branch key id or version.
- Mitigation: every attribute except `enc` (branch key id, type, version, kms-arn, hierarchy version, custom context, `tablename` = logical name) is placed in the KMS encryption context and authenticated by KMS Decrypt/ReEncrypt as AAD (`kms_ops::build_authenticated_encryption_context`; spec branch-key-store.md).
- Residual: relies on the reconstructed context matching the write-time context exactly. This is the top verification target (VR-2026-T01).

TM-MPL-013: Branch-key AAD inconsistency.

- Attack: wrap and unwrap compute different AAD, breaking context binding.
- Mitigation: `compute_aad` builds `"aws-kms-hierarchy"`, branch key id, 16-byte version and serialized context identically on wrap and unwrap. The version is parsed strictly as a 36-character canonical UUID (`branch_key_wrap.rs`; spec hierarchical-keyring.md).
- Residual: encryption-context serialization determinism and version-format strictness are verification targets.

TM-MPL-016: VersionKey optimistic-lock bypass.

- Attack: a version race overwrites the ACTIVE record.
- Mitigation: a single `TransactWriteItems` uses the condition `attribute_exists(branch-key-id) AND enc = :encOld` for ACTIVE and `attribute_not_exists` for the new DECRYPT_ONLY record, with KMS ReEncrypt re-authenticating the old ACTIVE record (`branch_key_store::version_key`).
- Residual: none stated; DynamoDB transaction semantics are an external assumption.

TM-MPL-017: Reproduced-context merge tampering.

- Attack: the merge drops or alters bound context so decryptor AAD differs from encryptor AAD.
- Mitigation: `merge_reproduced_encryption_context` fails when a shared key has different values, and appends reproduced-only pairs as required encryption context keys (`default_cmm.rs`; spec cmm-interface.md).
- Residual: this is the only guard that decryptor AAD equals encryptor AAD; it is a verification target.

### Repudiation

TM-MPL-020: No audit binding between MPL operations and KMS/DynamoDB calls.

- Attack: an operation cannot be tied to the KMS and DynamoDB calls it caused.
- Mitigation: KMS and DynamoDB CloudTrail, and the `aws-kms-hierarchy` user agent.
- Residual: low; this is an operational control outside the library.

### Information disclosure

TM-MPL-010: Shared-cache confusion.

- Attack: two keyrings with the same partition id, logical name and branch key id share entries. A keyring without direct KMS access reuses materials, or a non-committing entry is reused where commitment is expected.
- Mitigation: the default partition id is a fresh random v4 UUID, so caches are isolated by default. Shared scope is opt-in and documented as must-match-only-if-intended.
- Residual: no cross-check that a cached suite's commitment matches the current policy. This relates to the shared-cache commitment-bypass advisory class; the specific identifier CVE-2026-6550 / GHSA-v638-38fc-rhfv is UNVERIFIED (see section 10).

TM-MPL-015: No zeroization of secret material.

- Attack: a memory adversary (TA4) reads freed heap, swap or core dumps that still hold key bytes.
- Mitigation: none automatic. There is no Drop-driven zeroization for `BranchKeyMaterials.branch_key`, derived-key locals, `PlaintextDataKey` (which has a manual `zeroize` that is not called on drop) or `RawAesKeyring.wrapping_key`. Debug output is redacted.
- Residual: secret bytes remain in memory after use. Verification can prove the manual `zeroize` is complete and in bounds, but not that secrets never outlive their scope.

TM-MPL-021: Secret leakage through Debug or logging.

- Attack: key bytes appear in Debug output, errors or logs.
- Mitigation: `RawAesKeyring` and `BranchKeyMaterials` redact Debug; errors carry messages, not key bytes.
- Residual: Debug redaction for `PlaintextDataKey` and `SigningKey` still needs confirmation.

### Denial of service

TM-MPL-018: Storm-tracking correctness.

- Attack: misconfiguration or a logic error causes a refresh stampede, deadlock or InFlightTTL failures.
- Mitigation: `ValidatedConfig::from_raw` enforces `grace_interval <= inflight_ttl <= grace_period` and all values at least 1. The lock is never held across `.await`. A put writes the inner cache before clearing the in-flight entry (`cmc/storm_tracking.rs`).
- Residual: the state machine is intricate (liveness and safety), and it runs only on Tokio (`tokio::time::sleep`). Strong verification target.

TM-MPL-022: Cache exhaustion forces a KMS call storm.

- Attack: eviction thrash drives repeated KMS calls and throttling.
- Mitigation: default 1000-entry LRU with TTL-aware pruning; storm tracking coalesces refreshes.
- Residual: none stated; capacity sizing is operational.

TM-MPL-023: Panic on malformed ciphertext.

- Attack: a crafted EDK or ciphertext makes the library panic instead of returning an error.
- Mitigation: `branch_key_wrap::unwrap` checks length against a fixed overhead before slicing; `try_decrypt_edk` checks bounds before reading the version; `uuid_str_to_16_bytes` returns an error rather than panicking.
- Residual: remaining `expect` calls rely on earlier length checks; panic-freedom is a verification candidate.

### Elevation of privilege

TM-MPL-006: Suite downgrade or commitment-policy bypass.

- Attack (Invisible Salamanders class): force decryption of a non-committing suite where commitment is required, or bypass commitment through the cache.
- Mitigation: `DefaultCmm.get_encryption_materials` rejects a suite that is not `allows_for_encrypt`; `decrypt_materials` rejects one that is not `allows_for_decrypt` (`default_cmm.rs`; spec commitment-policy.md).
- Residual: correctness of the per-suite allow tables; verification candidate.

TM-MPL-007: Discovery/MRDiscovery alias or attacker-region MRK.

- Attack: a Discovery or MRDiscovery configuration decrypts a record under an alias or an MRK in an attacker-chosen region.
- Mitigation: `resolve_keystore_arn` rejects alias ARNs and, for MRDiscovery, rewrites only the region to the configured region (`kms_ops.rs`; spec branch-key-store.md).
- Residual: `parse_arn` and the region-rewrite string handling are verification targets.

TM-MPL-008: Non-committing suite reuse (Invisible Salamanders).

- Attack: a non-committing suite is used where key commitment is expected (Dodis et al., IACR ePrint 2019/016; AWS S3EC key-commitment advisory).
- Mitigation: as TM-MPL-006; commit-key suites are the default under REQUIRE policies.
- Residual: same allow-table dependency as TM-MPL-006.

TM-MPL-009: Cache-identifier collision.

- Attack: two distinct requests map to the same cache identifier and receive the wrong branch-key materials.
- Mitigation: identifier = SHA-384 over the null-separated resource id, scope, partition, logical name, branch key id and optional version (`cache_entry_identifier.rs`; spec hierarchical-keyring.md Appendix A).
- Residual: separator and domain-separation correctness, and the second-preimage assumption; verification candidate.

TM-MPL-011: AES-GCM IV reuse in the raw-AES keyring.

- Attack: a repeated nonce under the same wrapping key compromises confidentiality and authenticity.
- Mitigation: a fresh 12-byte IV from the CSPRNG on every `on_encrypt`, passed to `prim::aes_encrypt` (`Nonce::try_assume_unique_for_key`) (`raw_aes_keyring.rs`, `prim/src/lib.rs`).
- Residual: uniqueness rests on a 96-bit random nonce, so reuse is bounded by the birthday bound. Prime verification target.

TM-MPL-012: Salt/IV reuse in branch-key wrap.

- Attack: a repeated salt and IV pair under the same branch key.
- Mitigation: a fresh 16-byte salt and 12-byte IV on every `wrap` (224 bits). The spec's Appendix B birthday analysis gives 2^96 wraps before a 2^-32 collision probability, which motivates yearly rotation (`branch_key_wrap::wrap`).
- Residual: probabilistic bound plus rotation cadence. Verification target alongside TM-MPL-011.

TM-MPL-014: KBKDF fixed-info misuse.

- Attack: a wrong fixed-info layout or L value weakens derivation.
- Mitigation: fixed-info = label `"aws-kms-hierarchy"`, 0x00, salt, big-endian 32-bit L = 256 (NIST SP 800-108 counter-mode HMAC-SHA-256) via `prim::kbkdf_ctr_hmac`, 32-byte output (`branch_key_wrap::derive_branch_key`).
- Residual: byte layout and L value correctness; strong verification candidate.

TM-MPL-019: Missing Duvet coverage.

- Attack: a spec MUST regresses without any mechanical trace catching it.
- Mitigation: none on this branch; annotations live on `duvet/mpl-annotations`.
- Residual: spec MUSTs are not traced to code or tests. Recommendation: add Duvet annotations for commitment policy, MRK match, AAD, cache id and key-store authentication requirements.

## 9. Recommendations

### 9.1 Configuration

- Prefer single-key `KmsKeyArn` or `KmsMrKeyArn` over Discovery modes (TM-MPL-002, TM-MPL-007).
- Default to REQUIRE_ENCRYPT_REQUIRE_DECRYPT and commit-key suites (TM-MPL-006, TM-MPL-008).
- Set a unique partition id only when cache sharing is intended (TM-MPL-010). This is the source wording; see Appendix A, note 8.
- Keep the storm-tracking TTL much larger than the grace period, on a Tokio runtime (TM-MPL-018).

### 9.2 Implementation

- Add zeroize-on-drop for secret-bearing types (TM-MPL-015).
- Add Duvet annotations to this branch (TM-MPL-019).
- Move ARN parsing into a verified module (TM-MPL-004, TM-MPL-007).
- Add a cache-entry check that a served suite's commitment matches the current policy (TM-MPL-010).

### 9.3 Operational

- Rotate branch keys about yearly (TM-MPL-012).
- Scope KMS grants tightly (TM-MPL-002).
- Enable CloudTrail on the KMS keys and the DynamoDB table (TM-MPL-020).

## Appendix A. Editor's notes

These notes record differences between sources, or editorial choices. In every case the threat model's value is kept.

1. Mitigation status column. The source has no mitigation-status field. The values in the register are an editorial summary of each threat's mitigation and residual text in source section 8. They are not ratings and should be reviewed.
2. TM-MPL-010 category. Source section 7 lists TM-MPL-010 under Information Disclosure, while source section 8 and the risk matrix label it I/E. This document uses I/E. `docs/verification-targets.md` section 4 counts it under Information Disclosure, consistent with section 7.
3. TM-MPL-023 residual rating. The residual-risk table rates TM-MPL-023 "Low-Med", while the risk matrix rates its risk Low. Both are reproduced as given.
4. TM-MPL-015 wording. Source sections 5 (TB6) and 9 say "no zeroization", while section 8 notes that `PlaintextDataKey` has a manual `zeroize` that is not Drop-driven. This document uses the section 8 wording, which is the more precise. `docs/verification-targets.md` target T08 targets that manual `zeroize`.
5. Likelihood source. For TM-MPL-003, 008, 013, 014, 016, 017, 019, 020, 021, 022 and 023, source section 8 gives only severity and risk, not likelihood. Likelihood values here come from the source's risk matrix appendix. Where section 8 does give values, they match the matrix.
6. Commit. The code reviewed is commit a1e23d7, as stated in the bug reports. Commits a4f4693 and bbb8ec2 on MPL-Verus add documentation and pipeline files only; `mpl/src`, `prim/src` and `esdk/src` are unchanged from a1e23d7 there. The later merge commit c256243 ("Merge main into MPL-Verus") brings in upstream changes to `mpl/src` and `prim/src`, including a raw AES keyring change. This document has not been re-checked against that merge; reviewers should treat a1e23d7 as the analyzed revision. The bug reports alone were re-checked against `main` `620771c` (`docs/bug-reports/RECHECK-main-620771c.md`); the bug status shown in section 7 comes from that re-check. Threats and ratings are unchanged.
7. Bug-to-threat links. BUG-02 and BUG-08 list only capability-driven targets (VR-2026-C04, VR-2026-C01) in their Related IDs and are therefore not mapped to threats. BUG-07 also lists VR-2026-C03 in addition to its threat-linked target.
8. Partition-id recommendation. Source section 11 says "set a unique partition-id only when cache sharing is intended". Read with the TM-MPL-010 mitigation (the default partition id is a fresh random UUID, and sharing is opt-in), the likely intent is to set an explicit partition id, matching across the keyrings that share, only when sharing is intended. The source wording is kept; reviewers should confirm the intent.
