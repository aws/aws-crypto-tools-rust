Top risks.

- TM-MPL-009 and TM-MPL-010, cache-identifier collision and shared-cache confusion: High (Severity High, Likelihood Medium). BUG-06 is open on `main` and was confirmed end to end: with one shared cache, keyring B was served key store A's branch key. The preconditions are a shared cache plus a NUL-containing partition id, logical key store name or branch key id.
- TM-MPL-005, branch-key record substitution: High (Severity Critical, Likelihood Medium). It is mitigated by binding every record attribute into the KMS encryption context, so correctness depends on the reconstructed context matching the write-time context exactly. The freshness of the ACTIVE record is not checked, so an authentic older record can be replayed by someone with DynamoDB write access.
- TM-MPL-011 and TM-MPL-012, AES-GCM IV and salt reuse: Critical severity, Medium risk. Uniqueness rests on CSPRNG randomness, not counters.
- TM-MPL-002, TM-MPL-004, TM-MPL-007, KMS key and ARN confusion: Critical or High severity, Medium risk. Pinned-ARN modes are mitigated. Discovery modes trust the record's ARN on encrypt as well as decrypt, and ARN parsing is unverified string handling.
- TM-MPL-006 and TM-MPL-008, commitment-policy bypass (Invisible Salamanders class): Medium risk. It depends on the correctness of the per-suite allow tables.
- TM-MPL-018 and TM-MPL-025, storm-tracking correctness and decrypt-input amplification: Medium risk. TM-MPL-025 is new and provisional (static reasoning, not run): the sender of a ciphertext controls the EDK count and the branch-key version bytes, and by default nothing caps them.
- TM-MPL-024, the C++ shim handle boundary: Medium risk. It is the only `unsafe` code that reaches MPL objects. `mpl/src` and `prim/src` contain no `unsafe` code.

What improved since `a1e23d7`: zeroize-on-drop for all long-lived secret types, constant-time comparison of secrets, plaintext-data-key length enforcement (BUG-02), strict encryption-context decoding (BUG-03), an exact cache-TTL comparison (BUG-09), materials-transition checks on every `send()`, and an error model that never carries EDK ciphertext.

## 2. Scope and assumptions

### 2.1 In scope

- `mpl/` key management: `RawAesKeyring`, `HierarchicalKeyring`, `branch_key_wrap`, `cache_entry_identifier`, `mrk_match`, `DefaultCmm`, commitment policy and algorithm suites, the DynamoDB key store (`key_store/`), `kms_ops`, `kms_config`, `record`, the local cache (`cmc/local`) and the storm-tracking cache (`cmc/storm_tracking`).
- `prim/` (`aws-mpl-primitives`): safe wrappers for AES-GCM, KBKDF, HKDF, HMAC, digest, ECDSA and the CSPRNG.
- Secret-material lifetime in process memory.
- The C++ shim handle boundary (`esdk/shims/aws-esdk-cpp`) as the way C++ callers reach MPL objects (TM-MPL-024).
- The four loopback test servers, as a test-only surface (TM-MPL-026).
- The specification in `spec/framework/*.md` as the reference for intended behavior.

### 2.2 Out of scope

- ESDK message format: header and body serialization, framing, and message-level signature verification. The ESDK and the C++ shim appear only as callers.
- The internals of AWS KMS, Amazon DynamoDB and aws-lc-rs, beyond the guarantees listed as assumptions.
- Application logging and the correctness of caller-supplied code such as a custom `BranchKeyIdSupplier`, `KeyStore` or `Cmc`.

### 2.3 Assumptions

- The process, the local AES wrapping key and the in-process cache are trusted.
- AWS KMS is the root of trust for branch and beacon keys and enforces the encryption context as AAD.
- DynamoDB is untrusted for integrity. Records are made tamper-evident, but not fresh, by KMS encryption-context binding.
- Network traffic to KMS and DynamoDB uses TLS. Residual network threats are downgrade and denial of service.
- aws-lc-rs is reached only through the safe `prim` wrappers.
- Cryptographic primitives (AES-GCM, HMAC-SHA-256, SHA-384) are secure.
- `main` has no Duvet configuration for the MPL. `mpl/` and `prim/` contain exactly one annotation block (`mpl/src/cmc/entry.rs:201-204`), which CI does not check. Mitigations cite code locations and spec sections directly. This gap is tracked as TM-MPL-019.

## 3. System overview

### 3.1 Components

| Component | Location | Role |
|---|---|---|
| DefaultCmm | `cmm/default_cmm.rs` | Resolves the algorithm suite under the commitment policy, generates ECDSA keys for signing suites, merges the reproduced encryption context on decrypt |
| SharedCmm / SharedKeyring `send()` | `cmm/fluent_builders.rs`, `keyring/fluent_builders.rs`, `structures/materials_checks.rs` | Materials checks: the CMM output is checked for completeness; every keyring call is checked for a legal transition |
| RawAesKeyring | `keyring/raw_aes_keyring.rs` | Wraps data keys locally with AES-GCM under a long-lived wrapping key |
| HierarchicalKeyring | `aws_kms/hierarchical_keyring.rs` | Wraps data keys under KMS-protected branch keys, using the cache and the key store |
| branch_key_wrap | `aws_kms/branch_key_wrap.rs` | KBKDF derivation of a per-wrap key and AES-256-GCM wrap/unwrap with bound AAD |
| cache_entry_identifier | `aws_kms/cache_entry_identifier.rs` | SHA-384 cache identifier over scope, partition, logical name, branch key id and version |
| mrk_match | `aws_kms/mrk_match.rs` | MRK-aware ARN matching for decrypt |
| Cryptographic materials cache (Cmc) | `cmc/local.rs`, `cmc/storm_tracking.rs`, `cmc/default.rs` | In-process cache of branch-key materials with TTL. The default cache (with `rt-tokio`) is storm tracking over a local LRU |
| DynamoDbKeyStore | `key_store/branch_key_store.rs` | Reads and writes branch-key records in DynamoDB; creates and versions keys |
| kms_ops, kms_config, record | `key_store/` | KMS calls with an authenticated encryption context, ARN validation, record-to-materials mapping |
| prim | `prim/src/lib.rs` | The only primitive crypto surface; safe wrappers over aws-lc-rs |
| C++ shim | `esdk/shims/aws-esdk-cpp/` | `cxx` bridge that hands C++ callers raw handles to keyrings, key stores, caches and SDK clients |
| Test servers | `mpl/test-server`, `prim/test-server`, `esdk/test-server`, `esdk/shims/aws-esdk-cpp/test-server` | Loopback CBOR servers for cross-implementation tests; not published |

### 3.2 Architecture and data flow

```
                Caller (ESDK / C++ shim / DB-ESDK / S3EC)
                                 |
        SharedCmm: get_encryption_materials / decrypt_materials  .send()
                                 v
   +---------------------------------------------------------------+
   | send(): check output materials are complete                   |
   |   DefaultCmm: commitment policy + suite, ECDSA keygen,        |
   |   reproduced-EC merge                                         |
   +---------------------------------------------------------------+
                                 |  SharedKeyring: on_encrypt / on_decrypt  .send()
                                 v
   +---------------------------------------------------------------+
   | send(): check materials transition (before, after)            |
   |   RawAesKeyring                 HierarchicalKeyring           |
   +---------------------------------------------------------------+
        |                              |                 |
   AES-GCM (prim)              Cmc cache            DynamoDbKeyStore
   local wrapping key          (storm tracking      |          |
   (zeroize on drop)            over local LRU)   AWS KMS   Amazon DynamoDB
                               (in-process)       (EC as AAD) (branch-key records)
                                    |
                          branch_key_wrap (KBKDF + AES-256-GCM)
                                    |
                              prim (aws-lc-rs)
                  AES-GCM / KBKDF / HKDF / HMAC / ECDSA / digest / RNG
                                    |
                    aws-lc-rs FFI (no `unsafe` in mpl/ or prim/)

   C++ callers --> aws-esdk-cpp shim (cxx bridge) --> keyrings / key stores / caches / clients
        raw `*const T` handles (borrowed) and a type-erased `void*` (`Keyring::adopt`)
```

Diagram in prose. A caller (ESDK, C++ shim, DB-ESDK or S3EC) asks a CMM for encryption or decryption materials. The DefaultCmm resolves the algorithm suite under the commitment policy, generates an ECDSA key pair for signing suites, and on decrypt merges the reproduced encryption context. Every `send()` on a built-in CMM or keyring runs the materials checks. The CMM then calls a keyring's on_encrypt or on_decrypt. The RawAesKeyring wraps the data key directly with AES-GCM under a local wrapping key. The HierarchicalKeyring looks up branch-key materials in the in-process cache. On a miss it asks the key store, which reads the record from DynamoDB and has AWS KMS decrypt it. The branch key is then used by branch_key_wrap, which derives a per-wrap key with KBKDF and wraps the data key with AES-256-GCM. All primitive cryptography goes through the prim crate, which is the only code that reaches the aws-lc-rs FFI.

Encrypt path (hierarchical keyring). The keyring resolves the branch key id (static, or from a supplier given the encryption context) and computes cache id = SHA-384(0x02, 0x00, 0x01, 0x00, partition, 0x00, logical name, 0x00, branch key id). On a cache miss it calls the key store for the active branch key (KMS Decrypt with the encryption context as AAD) and caches the result with a TTL. It then derives a key with KBKDF(salt) and seals the data key with AES-256-GCM, with AAD = label, branch key id, version, encryption context. The EDK has provider id `aws-kms-hierarchy`, provider info = branch key id, and ciphertext = salt, IV, version, encrypted key, tag.

Decrypt path (hierarchical keyring). The CMM checks that the suite is allowed for decrypt and merges the reproduced encryption context. The keyring filters EDKs by provider id and branch key id and tries each match one after another. For each, it parses the 16-byte version from ciphertext bytes 28 to 44 and computes cache id = SHA-384(0x02, 0x00, 0x02, 0x00, partition, 0x00, logical name, 0x00, branch key id, 0x00, version). It obtains the branch-key materials from the cache or key store, derives the key with KBKDF(salt), and opens the AES-256-GCM ciphertext. A failed key-store read is not cached.

### 3.3 Trust boundaries

| ID | Boundary | What crosses | Controls |
|---|---|---|---|
| TB1 | Caller or ciphertext sender to MPL API | Materials requests, encryption context, EDKs, suite id | CMM validation, reserved-key checks, commitment policy, materials checks on `send()`. On decrypt, nothing in the MPL bounds the EDK count (TM-MPL-025) |
| TB2 | MPL to AWS KMS | GenerateDataKeyWithoutPlaintext, ReEncrypt, Decrypt | KMS authentication, encryption context as AAD, key-ARN restriction, grant tokens |
| TB3 | MPL to DynamoDB | GetItem, TransactWriteItems | KMS encryption-context binding makes records tamper-evident; conditional writes. `GetItem` is not a consistent read, so freshness is not guaranteed |
| TB4 | Keyring to in-process cache | Cache put and get | SHA-384 cache identifier (not injective with NUL, BUG-06), exact TTL, materials-kind check |
| TB5 | `mpl`/`prim` to aws-lc-rs FFI | AES-GCM, KDF, ECDSA, RNG calls | Safe `prim` wrappers, length checks, `Nonce::try_assume_unique_for_key` |
| TB6 | Process memory to OS | Freed heap, swap, core dumps | Zeroize-on-drop for secret types, `Debug` redaction. Transient copies remain (TM-MPL-015) |
| TB7 | MPL to user-supplied components | `KeyStore`, `Cmc`, `BranchKeyIdSupplier`, user `Keyring` and `Cmm` | Built-in keyring and CMM output is checked by `send()`. Key store, cache and supplier output is not checked; only the material kind of a cache entry is |
| TB8 | C++ to shim to MPL | Raw handle pointers (borrowed) and a type-erased keyring pointer (adopted) | Null checks on borrow only; none on adopt |
| TB9 | Loopback client to test server to MPL | CBOR requests on `127.0.0.1` that build keyrings and AWS clients | Loopback bind only; no authentication. Not published (`publish = false`) |

## 6. Threat details

Each entry gives the attack, the existing mitigation as described in the source, and the residual risk. Ratings are in the register above. "Second pass" marks text that was added or re-derived after the first pass of the source document. Items marked "static reasoning" were found by reading code and were not run.

### Spoofing

TM-MPL-001: Raw-AES key-provider-id impersonation.

- Attack: a caller sets the key namespace to `aws-kms` or `aws-kms-hierarchy` so its EDKs look like KMS-keyring EDKs.
- Mitigation: `RawAesKeyringBuilder::build` (`mpl/src/keyring/raw_aes_keyring.rs:350`) rejects any namespace that starts with `aws-kms` (constant `:52`, check `:360`).
- Residual: the check is a prefix test on the exact bytes. Other keyrings compare the provider id exactly, so a case variant does not impersonate.

TM-MPL-002: Branch-key record decrypts under an attacker-influenced KMS key.

- Attack: a DynamoDB tamperer (TA1) writes a record whose `kms-arn` points at an attacker-controlled key.
- Mitigation: for `KmsKeyArn` and `KmsMrKeyArn` configurations, `resolve_key_store_arn` sends the configured ARN as the KMS `KeyId` after the compatibility check (`mpl/src/key_store/kms_ops.rs:88`, `:94-95`, `:105`). `DynamoDbKeyStore::build` validates the configured ARN (`key_store/branch_key_store.rs:381`).
- Residual: by spec, Discovery modes trust the record's ARN (`kms_ops.rs:96-103`).
- Second pass: Discovery is not decrypt-only in this code. The hierarchical keyring calls `get_active_branch_key` on encrypt (`hierarchical_keyring.rs:692`), which runs the same `decrypt_branch_key` with the record's ARN (`branch_key_store.rs:792`, `:801`). A TA1 who can write the table, and who controls a KMS key whose key policy lets the application's role call Decrypt, can plant an ACTIVE record whose branch key the attacker knows, and new encryptions then wrap data keys under it. The preconditions (Discovery or MRDiscovery configured, DynamoDB write, an attacker key policy, no IAM scoping of `kms:Decrypt`) keep Likelihood at Low. The control is configuration: use a single-key configuration, or scope `kms:Decrypt` in IAM. BUG-04 does not widen this threat, because an attacker who can write the record already controls the ARN's region and account.

TM-MPL-003: Malicious or message-driven branch-key supplier.

- Attack: a caller-provided supplier returns an attacker-chosen branch key id.
- Mitigation: the supplier is caller-provided trusted code (public trait, `hierarchical_keyring.rs:187`). The resolved id is bound into the cache id (`:665`, `:908`) and the EDK provider info (`:722`), and the AAD uses the id of the returned materials (`branch_key_wrap.rs:61`), so a mismatched id fails authentication on decrypt.
- Residual: a supplier that returns ids containing `0x00` is one of the BUG-06 collision paths (rated under TM-MPL-009). Second pass: on decrypt the supplier's input is the message's encryption context (`hierarchical_keyring.rs:747`, `:831`), which the sender controls and which is not authenticated until a data key is recovered. So whoever submits a ciphertext picks the branch-key id the service looks up, as long as the EDK's provider info names the same id. The service's own role then fetches and caches any tenant's branch key on request. No key reaches the sender, because unwrap still needs the right key. The error type distinguishes an unknown version from an authentication failure, which is a small existence oracle if errors reach the sender. Deciding which tenant ids may be decrypted is the application's job, so the rating stays Low.

### Tampering

TM-MPL-004: Over-permissive ARN/MRK match.

- Attack: match logic accepts a key ARN that should not match.
- Mitigation: `aws_kms_mrk_match_for_decrypt` rejects aliases (`mpl/src/aws_kms/mrk_match.rs:24-27`; it returns `false` even for two identical alias ARNs, a documented spec deviation that fails closed). It returns true only on byte equality or, for MRK ARNs (`is_multi_region_arn`, `:52`), when every part except the region is equal. `is_arn_compatible` is at `mpl/src/key_store/kms_config.rs:86`.
- Residual: ARN parsing uses ad-hoc `split(':')` string parsers; the source calls this a strong verification candidate. The private `rewrite_arn_region` and `reject_alias_arn` have no direct tests.

TM-MPL-005: Branch-key record substitution or rollback.

- Attack: swap in a valid record from another branch key id or version, or replay an older ACTIVE record.
- Mitigation: every attribute except `enc` (branch key id, type, version, kms-arn, hierarchy version, create time, custom context, `tablename` = logical name) is placed in the KMS encryption context and authenticated by KMS Decrypt or ReEncrypt as AAD (`key_store/branch_key_store.rs:132-136`; `kms_ops::build_authenticated_encryption_context`, `mpl/src/key_store/kms_ops.rs:49`). Materials are rebuilt only from the authenticated context, with a strict 32-byte branch-key check (`key_store/record.rs:95`, `:164`).
- Residual: correctness rests on the reconstructed context exactly matching the write-time context. This is the top verification target (VR-2026-T01). A user-supplied `KeyStore` sits outside this mitigation, and the keyring does not compare the returned materials' id and version with the request (`hierarchical_keyring.rs:692-696`, `:934-939`; `key_store/client_impl.rs:305-308`, `:373-376`), although on decrypt the AAD still binds them. BUG-08 (a dead collision `Err` in `key_store/encryption_context.rs:91-102`) is informational and does not affect the rating.
- Second pass, authentic-record rollback: an older ACTIVE record of the same branch key id is a valid, KMS-authenticated record. A TA1 with DynamoDB write access can put an earlier copy of the ACTIVE item back, and `get_active_branch_key` accepts it. The keyring then encrypts under an older branch-key version. No key is disclosed, and decrypt of existing messages is unaffected because the version comes from the EDK. The effect is a rotation rollback, which matters because rotation bounds the salt and IV birthday risk (TM-MPL-012). Nothing detects it: `fetch_record` uses a plain `GetItem` with no consistent-read flag (`branch_key_store.rs:148`, `:155-163`), and the keyring does not remember the highest version it has seen. VersionKey's optimistic lock (`:752`) protects concurrent rotations by the library, not against table tampering. The rating is unchanged because the core property (a record cannot be forged or moved to another id or version) holds.

TM-MPL-013: Branch-key AAD inconsistency.

- Attack: wrap and unwrap compute different AAD, breaking context binding.
- Mitigation: `compute_aad` builds the label `aws-kms-hierarchy`, branch key id, 16-byte version and serialized context the same way on wrap and unwrap (`branch_key_wrap.rs:61`). The version is parsed strictly as a 36-character canonical UUID (`:92`). `EncryptionContext::from_bytes` rejects out-of-order and duplicate keys and invalid UTF-8 (`mpl/src/structures/encryption_context.rs:145`; BUG-03, fixed), so a decoded context has one canonical form.
- Residual: serialization determinism and version-format strictness are unproven. `from_bytes` still accepts empty keys (`mpl/tests/test_encryption_context.rs:468`).

TM-MPL-016: VersionKey optimistic-lock bypass.

- Attack: a version race overwrites the ACTIVE record.
- Mitigation: VersionKey authenticates the ACTIVE record with a KMS ReEncrypt-to-self, then writes in one `TransactWriteItems`: `attribute_not_exists` for the new DECRYPT_ONLY item (`branch_key_store.rs:743`) and `attribute_exists(#branch_key_id) AND #enc = :encOld` for ACTIVE (`:752`). The function is at `version_key` (`:641`).
- Residual: none stated. A stale `GetItem` makes the condition fail and surfaces as a conflict; it does not corrupt the table.

TM-MPL-017: Reproduced-context merge tampering.

- Attack: the merge drops or alters bound context so decryptor AAD differs from encryptor AAD.
- Mitigation: `merge_reproduced_encryption_context` fails when a shared key's values disagree and appends reproduced-only pairs as required encryption context keys (`mpl/src/cmm/default_cmm.rs:198`, `:273`). The transition checks reject a keyring that changes the context or the required keys (`structures/materials_checks.rs:82-89`).
- Residual: the merge is still the only guard that the decryptor's AAD equals the encryptor's. It is a verification target.

### Repudiation

TM-MPL-020: No audit binding between MPL operations and KMS/DynamoDB calls.

- Attack: an operation cannot be tied to the KMS and DynamoDB calls it caused.
- Mitigation: KMS and DynamoDB CloudTrail. Every KMS call carries the framework metadata `AwsCryptographicMPL-Rust/<version>` in its user agent (`mpl/src/aws_kms/user_agent.rs:9`, `:15-19`).
- Residual: CloudTrail can attribute KMS calls to the MPL, but not to a specific MPL operation or message. This is an operational control outside the library.

### Information disclosure

TM-MPL-010: Shared-cache confusion.

- Attack: two keyrings that should be isolated share cache entries, so one reuses branch-key materials it could not fetch itself.
- Mitigation: the default partition id is a fresh random v4 UUID (`hierarchical_keyring.rs:626`), so caches are isolated by default. Shared scope is opt-in. The cache returns only `BranchKey` entries to the keyring (kind check `:1000`). Entries older than the TTL are refetched, with an exact comparison (`:989-995`; BUG-09, fixed).
- Residual: BUG-06 is a concrete, confirmed way to realize this threat across keyrings that have different partition ids (see TM-MPL-009). A user-supplied `Cmc` can return any entry for any id, and only its kind is checked. It can also report `grace_period() = None` (trait default, `mpl/src/cmc/mod.rs:88-90`), which skips the grace-versus-TTL check. The earlier residual "no cross-check that a cached suite's commitment matches the current policy" is withdrawn: the keyring caches only `CachedMaterials::BranchKey` (`:700`, `:943`), and branch keys do not depend on the commitment policy. TM-MPL-009 and TM-MPL-010 share one root cause and one fix.
- Second pass: (1) two physical key stores configured with the same logical name, partition id and branch key id share cache ids with no NUL involved. The spec forbids this configuration, and nothing in the MPL can detect it. (2) `cache_entry_within_limits` maps a `duration_since` error to zero elapsed (`hierarchical_keyring.rs:991-994`), so an entry whose creation time is in the future counts as fresh. This matches the spec formula, and the effect is bounded by the clock step.
- Advisory note: CVE-2026-6550 / GHSA-v638-38fc-rhfv is VERIFIED and does not apply here (see TM-MPL-008).

TM-MPL-015: Secret material not zeroized or kept past its use.

- Attack: a memory adversary (TA4) reads freed heap, swap or core dumps that still hold key bytes.
- Mitigation: zeroize-on-drop covers every long-lived secret type: `PlaintextDataKey`, `SigningKey` and `SymmetricSigningKey` (`mpl/src/structures/algorithm_suite.rs:505`, `:571`, `:655`), `BranchKeyMaterials` and `BeaconKeyMaterials` with their builders (`branch_key_materials.rs:205-219`, `beacon_key_materials.rs:221-235`), and the raw-AES wrapping key (`raw_aes_keyring.rs:72-78`). The derived branch key is `Zeroizing` (`branch_key_wrap.rs:135`). `mpl/src` and `prim/src` contain no `unsafe` code.
- Residual: transient and error-path copies remain: the raw-AES decrypt buffer on error paths (`raw_aes_keyring.rs:471`, `:489`), the `Vec` returned by `branch_key_wrap::unwrap`, the KMS SDK response `Blob` (`kms_ops.rs:207`), and BUG-07(a) (`prim/src/lib.rs:185-188`: `aes_encrypt` leaves plaintext in the caller's buffer on `Err`). By design, the cache holds plaintext branch keys for the TTL.
- Second pass: (1) residency can exceed the TTL. `LocalCmc` drops an expired entry only when it is read, when it falls in the pruned tail, or when it is evicted at capacity (`cmc/local.rs:69`, `:131`, `:166`), so an entry nobody reads stays in memory in plaintext. (2) `ecdsa_generate_keypair` holds the private key DER in a plain `Vec` inside `SignatureKeyPair`, which is not zeroizing (`prim/src/ecdsa.rs:324-326`, `:387`); on the length-check error path (`:391-392`) it is dropped without a wipe. Both residuals need TA4, who is already inside the process, so the likelihood stays Low. The risk fell from Medium to Low since the previous edition (Severity High to Medium).

TM-MPL-021: Secret leakage through Debug, errors or logging.

- Attack: key bytes or attacker-supplied text appear in Debug output, errors or logs.
- Mitigation: `Debug` is redacted for `PlaintextDataKey`, `SigningKey`, `SymmetricSigningKey`, `BranchKeyMaterials`, beacon keys, the raw-AES keyring and `SignatureKeyPair` (for example `algorithm_suite.rs:564`, `:612`, `:696`; `prim/src/ecdsa.rs:335`). The error model attaches EDK info as `DataKeyInfo`, which holds the provider id and info but never the ciphertext.
- Residual (second pass): `NoMatchingDataKey` keeps the message's EDK identities (`mpl/src/error/generated.rs:1064`, getter `:1591`). The provider info is a KMS key ARN (with an account id) or a branch-key id taken from attacker-supplied message bytes. It is not secret, but it is attacker-controlled text and an account-id disclosure if errors are logged verbatim or returned to the sender.

### Denial of service

TM-MPL-018: Storm-tracking correctness.

- Attack: misconfiguration or a logic error causes a refresh stampede, deadlock, InFlightTTL failures or a wedge.
- Mitigation: fan-out bounds concurrent refreshes (`mpl/src/cmc/storm_tracking.rs:274`, `:310`). The lock is never held across `.await`. A poisoned lock maps to an `Internal` error instead of a panic on the hot path (`:248`). A put writes the inner cache before it clears the in-flight mark (`:721`, `:725`).
- Residual, mitigation regressed (first pass): `StormTrackingCmcBuilder::build` (`mpl/src/cmc/storm_tracking.rs:606`) no longer enforces the spec ordering "Grace Interval <= Grace Period" and "Inflight TTL <= Grace Period", nor the minimums for the grace period and grace interval. A test accepts `grace_period = 0` (`mpl/tests/test_storm_tracking_cmc.rs:388`). The spec also conflicts with itself on its default Inflight TTL (20 s) against its default Grace Period (10 s).
- Second pass, three liveness findings (static reasoning, rating kept): (1) a stale in-flight mark. A leader that never calls `put_cache_entry` (a key-store error, or a cancelled caller) leaves its key marked, and after `in_flight_ttl` (default 10 s) every miss for that key returns `Throttling` until a call for a different key prunes the mark (`mpl/src/cmc/storm_tracking.rs:249-255`, `:322-323`). A low-traffic, single-key, encrypt-only service is exposed. (2) A waiter blocked by a full fan-out has no deadline of its own (`:310-313`). (3) BUG-01 plus the state lock: the panics at `:333` and `:680` happen while the state mutex is held, so unwinding poisons it and every later call on that cache returns `Internal`. Only a configuration with an unbounded duration reaches it. If a reproducer confirms finding (1), the severity could rise to High; at Likelihood Low the risk would still be Medium. The attacker-driven side of these gaps is TM-MPL-025.

TM-MPL-022: Cache exhaustion forces a KMS call storm.

- Attack: eviction thrash drives repeated KMS calls and throttling.
- Mitigation: with `rt-tokio`, the default cache is storm tracking over a 1000-entry LRU with tail pruning (`hierarchical_keyring.rs:567-574`; `cmc/local.rs:166`). Without `rt-tokio`, the caller must supply a cache (`hierarchical_keyring.rs:575-581`).
- Residual: a failed key-store lookup is never put in the cache (`hierarchical_keyring.rs:931-955`), so unknown versions cannot evict legitimate entries. Eviction pressure needs valid versions, which are bounded by the number of rotations. The remaining cost of unknown versions is key-store reads (TM-MPL-025).

TM-MPL-023: Panic or resource blow-up on malformed input or extreme configuration.

- Attack: a crafted EDK or ciphertext, or an extreme configuration value, makes the library panic or consume resources instead of returning an error.
- Mitigation: `try_decrypt_edk` checks for at least 44 bytes before reading the version (`hierarchical_keyring.rs:879`). `branch_key_wrap::unwrap` checks for at least 60 bytes before slicing (`branch_key_wrap.rs:236`). `EncryptionContext::from_bytes` returns errors on malformed input. BUG-02 is fixed (the key length is checked, `hierarchical_keyring.rs:767`, `algorithm_suite.rs:547`). PR #186 removed an O(n squared) memory blow-up in the attacker-controlled EDK count.
- Residual: still open are BUG-05(a) (`.expect` on ECDSA keygen, `default_cmm.rs:137-138`), BUG-05(b) (a 44 to 59-byte EDK costs one key-store call before it is rejected), BUG-01(a/d) (a huge configured TTL panics, `hierarchical_keyring.rs:702`, `:945`), BUG-01(b/c) (see TM-MPL-018) and BUG-07(b) (`aes_decrypt` maps every callee error to "authentication tag did not match", `prim/src/lib.rs:215`, `:229`). These are configuration-driven or practically unreachable, so the rating is unchanged.

TM-MPL-025: Decrypt-input amplification (new, provisional; static reasoning, not run).

- Attack: the ciphertext sender (TA8, no credentials) controls the EDK count and each EDK's 16 version bytes. `HierarchicalKeyring::on_decrypt` processes every EDK that names the configured branch key id, one after another (`hierarchical_keyring.rs:751-772`, `:889-894`).
- Amplification paths: (1) one key-store read per EDK with an unknown version (`hierarchical_keyring.rs:901`, `:934`), with no negative caching. A message can list up to 65,535 EDKs (`mpl/tests/test_keyring_memory.rs:4`), and the ESDK cap `max_encrypted_data_keys` defaults to `None` (`esdk/src/config.rs:35`, `:42`). This happens before the header is authenticated. (2) Each distinct unknown version marks a cache id in flight and is never cleared (TM-MPL-018, finding 1). The default fan-out is 20 (`storm_tracking.rs:115`), so twenty distinct versions can make legitimate cache misses wait for up to the in-flight TTL, while cache hits are still served. (3) A repeated unknown version makes each duplicate wait about the 1 s grace interval, so N duplicates hold one request for about N seconds. (4) With a supplier, the sender also picks the branch key id, so valid foreign tenant ids cost one DynamoDB read and one KMS Decrypt each, once per TTL.
- Mitigation: only EDKs that name the configured (or supplier-chosen) branch key id are attempted (`hierarchical_keyring.rs:752-763`), the version must have 16 bytes (`:879`), a failed lookup cannot evict legitimate entries, cache hits survive a full fan-out, and #186 removed the memory growth. Not mitigated: the per-message EDK count, a per-message key-store budget, negative caching and an overall deadline.
- Residual: DynamoDB read capacity (and a KMS call per valid foreign version), request latency, and availability of cache-miss refreshes. Severity Medium (availability and cost; no confidentiality or integrity effect), Likelihood Medium, Risk Medium. Provisional because paths 2 and 3 need a reproducer. Path 1 follows directly from the code and the default configuration.

### Elevation of privilege

TM-MPL-006: Suite downgrade or commitment-policy bypass.

- Attack (Invisible Salamanders class): force encryption or decryption with a non-committing suite where commitment is required, or bypass commitment through the cache.
- Mitigation: `DefaultCmm` rejects a requested suite that is not `allows_for_encrypt` (`mpl/src/cmm/default_cmm.rs:97`) and a message suite that is not `allows_for_decrypt` (`:184`); the tables are at `mpl/src/structures/commitment_policy.rs:62`, `:77`. The transition check stops a keyring from changing the suite (`materials_checks.rs:78-81`) and runs on every `SharedKeyring` `send()`. The plaintext data key length is bound to the suite (`algorithm_suite.rs:547`; BUG-02, fixed). The ESDK checks the message's suite against its policy before calling the CMM (`esdk/src/decrypt.rs:413`) and re-checks the CMM's returned suite (`esdk/src/materials.rs:130`, `:202`).
- Residual: correctness of the per-suite allow tables, which are not proven and have no Duvet trace. The `FORBID_ENCRYPT_ALLOW_DECRYPT` default suite is `03 78` (`commitment_policy.rs:43-50`), a documented deviation from the spec's `00 78`; it is stronger and still non-committing. Second pass: `SharedCmm::send()` checks only that its output is complete (`cmm/fluent_builders.rs:171`, `:319`), so a user-written `Cmm` used by another consumer of the MPL has no policy backstop inside the MPL.

TM-MPL-007: Discovery/MRDiscovery alias or attacker-region key.

- Attack: a Discovery or MRDiscovery configuration decrypts a record under an alias or a key in an attacker-chosen region.
- Mitigation: `resolve_key_store_arn` rejects alias ARNs for both discovery modes (`kms_ops.rs:96-103`, `reject_alias_arn` `:118`).
- Residual: BUG-04 is open. The MRDiscovery arm rewrites the region of any record ARN, including single-Region keys (`kms_ops.rs:100-103`, `rewrite_arn_region` `:144`). The effect is a KMS call to an ARN that does not exist or names a different key, so it fails closed. The KMS-side behavior needs AWS and was not run.

TM-MPL-008: Non-committing suite reuse (Invisible Salamanders).

- Attack: a non-committing suite is used where key commitment is expected (Dodis et al., IACR ePrint 2019/016).
- Advisory: CVE-2026-6550 / GHSA-v638-38fc-rhfv is VERIFIED. It describes a key-commitment policy bypass in the AWS Encryption SDK for Python, in which two clients with different commitment policies share one `CachingCryptoMaterialsManager`, and the weaker-policy client encrypts first. It was fixed in ESDK for Python 3.3.1 and 4.0.5. It is scoped to the Python caching CMM and does not apply to this code: `mpl/src/cmm/` has no caching CMM, and the hierarchical keyring caches only branch keys, which do not depend on the commitment policy. Sources: [GitHub Advisory Database](https://github.com/advisories/GHSA-v638-38fc-rhfv), [aws-encryption-sdk-python advisory](https://github.com/aws/aws-encryption-sdk-python/security/advisories/GHSA-v638-38fc-rhfv), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-6550), [AWS Security Bulletin 2026-017-aws](https://aws.amazon.com/security/security-bulletins/2026-017-aws/). Content was rephrased for compliance with licensing restrictions.
- Mitigation: as TM-MPL-006. Commit-key suites (`05 78`) are the default under the REQUIRE policies (`commitment_policy.rs:43-58`).
- Residual: the same allow-table dependency as TM-MPL-006. `CachedMaterials::Encryption` and `Decryption` kinds exist (`mpl/src/cmc/entry.rs:26`, `:28`), so any future caching CMM must bind the commitment policy (or the suite) into its cache id.

TM-MPL-009: Cache-identifier collision.

- Attack: two distinct requests map to the same cache identifier and receive the wrong branch-key materials. The identifier is SHA-384 over `0x02 || 0 || scope || 0 || partition || 0 || logicalName || 0 || bkid [|| 0 || version]`, with single NUL separators and no length prefixes (`mpl/src/aws_kms/cache_entry_identifier.rs:35`, `:42-60`; call sites `hierarchical_keyring.rs:665`, `:908`). This is the layout the spec requires. The spec also says keyrings with different partition ids "CANNOT share" cache entries, and that holds only if no field contains `0x00`.
- Confirmed on main (BUG-06): keyring A uses partition `"tenant\0x"` and logical name `"L"`, and keyring B uses partition `"tenant"` and logical name `"x\0L"`, both with branch key id `"bk"`. The two preimages are identical. With one shared cache, A's OnEncrypt caches A's branch key, B gets a hit, never calls key store B, and wraps its data key under A's branch key. The same shift works between any two adjacent fields. Nothing checks the inputs: the partition id is the caller's raw bytes (`hierarchical_keyring.rs:596`), the default random 16-byte UUID can contain `0x00` (`:626`), the logical name is used as the key store returns it (`:600-605`), and the branch key id comes from configuration or a supplier. The only post-hit guard is the material-kind check (`:1000`).
- Rating: Severity High (cross-tenant use of a branch key), Likelihood Medium, Risk High. Second pass: re-derived and kept. The version field cannot be a NUL vector, because it is rendered as hex digits and hyphens (`hierarchical_keyring.rs:894`). What remains is a configuration precondition the MPL does not check: a shared cache, plus NUL-containing values from tenant names, from a user `KeyStore`'s logical name, or from a supplier driven by the encryption context. The source notes that reviewers who judge NUL-containing tenant input unrealistic could return this to Medium risk.
- Fix direction: reject `0x00` in these fields, or length-prefix them. Length-prefixing needs a spec change and breaks cross-runtime cache-id compatibility. Hierarchical tests cover cache-id separation but have no NUL case.

TM-MPL-011: AES-GCM IV reuse in the raw-AES keyring.

- Attack: a repeated nonce under the same wrapping key compromises confidentiality and authenticity.
- Mitigation: a fresh 12-byte IV from the CSPRNG on every wrap (`mpl/src/keyring/raw_aes_keyring.rs:146`, `:151-152`), passed to `prim::aes_encrypt` (`Nonce::try_assume_unique_for_key`, `prim/src/lib.rs:188`).
- Residual: uniqueness rests on a 96-bit random nonce, so reuse is bounded only by the birthday bound. NIST SP 800-38D limits a key to 2^32 invocations when the IV is random; the keyring keeps no wrap counter, and a long-lived wrapping key on a high-volume service can approach that over its life. There is no two-call IV-distinctness test. Prime verification target.

TM-MPL-012: Salt/IV reuse in branch-key wrap.

- Attack: a repeated salt and IV pair under the same branch key.
- Mitigation: a fresh 16-byte salt and 12-byte IV on every `wrap` (`mpl/src/aws_kms/branch_key_wrap.rs:157`, `:164`, `:170`). The salt gives a fresh derived key for each wrap. The spec's Appendix B birthday analysis motivates yearly rotation.
- Residual: probabilistic bound plus rotation cadence. The rollback residual under TM-MPL-005 can undo a rotation. Verification target alongside TM-MPL-011.

TM-MPL-014: KBKDF fixed-info misuse.

- Attack: a wrong fixed-info layout or L value weakens derivation.
- Mitigation: fixed info is the label `aws-kms-hierarchy`, `0x00`, the salt, and a big-endian 32-bit L = 256 (NIST SP 800-108 counter-mode HMAC-SHA-256), computed by `prim::kbkdf_ctr_hmac` (`prim/src/lib.rs:313`); the derivation is `derive_branch_key` (`branch_key_wrap.rs:122`) with a `Zeroizing` output.
- Residual: correctness of the byte layout and L value. Second pass: the spec gives the salt, key and label, but not the fixed-info byte layout. Interoperability with other MPL runtimes therefore rests on the code, and a proof can only be stated against the code. No Dafny conformance claim is made.

TM-MPL-019: Missing Duvet coverage.

- Attack: a spec MUST regresses without any mechanical trace catching it.
- Mitigation: none. `main` contains no MPL Duvet config; `mpl/` and `prim/` hold one annotation block (`mpl/src/cmc/entry.rs:201-204`), which no config checks. The spec is not a submodule since #91 (`6ef7d80`); it is fetched from `scripts/spec-source.json` at `ref = "master"`, so the spec revision floats.
- Residual: spec MUSTs are not traced to code or tests. Recommendation: add `mpl/.duvet/config.toml` and annotations for the commitment policy, MRK match, AAD, cache id, key-store authentication and storm-tracking constraints, and pin the spec revision.

TM-MPL-024: C++ shim handles (new since the first pass).

- Attack: a C++ caller (TA7) passes a dangling, forged or double-adopted pointer. The shim's `cxx` bridge (`esdk/shims/aws-esdk-cpp/src/lib.rs:167`) hands C++ opaque Rust resources. (a) Borrowed handles are `*const T`, null-checked and then dereferenced in `unsafe` (`require_handle`, `lib.rs:715`, `:720`, `:728`; optional clients and cache `:1570`, `:1571`, `:1661`). (b) An adopted keyring is a type-erased `void*` (`into_keyring_handle`, `lib.rs:2059-2066`) that C++ `Keyring::adopt` turns into a `rust::Box` with no null, type or ownership check (`src/EncryptionSDK.cpp:541-547`; header `include/aws/esdk/EncryptionSDK.h:656-664`). A wrong pointer is type confusion and a second adoption is a double free, in a process that holds keys.
- Mitigation: null checks on borrowed handles, typed `cxx` bindings, `Retained` dependencies in the C++ facade, and the lifetime rules in spec `shim/shim.md#handles-and-lifetimes`. The Rust side takes only shared references and holds no handle across `block_on`. Residual risk is concentrated in callers that bypass the facade, a handle freed on another thread between the null check and the clone, and `adopt`.
- Notes: #188 (`41f1d51`) moved the later `unsafe` lines down by 6 and changed no handle or lifetime path. #189 (`5f2dc72`) changed build and link only. This is the only `unsafe` code that reaches MPL objects. The owner is the shim, outside `mpl/` and `prim/`.

TM-MPL-026: Unauthenticated loopback test servers (new).

- Attack: four test-server crates bind `127.0.0.1` only and authenticate no one (`mpl/test-server/src/main.rs:26-27`; `prim/test-server/src/main.rs:23-24`; `esdk/test-server/src/main.rs:26-27`; `esdk/shims/aws-esdk-cpp/test-server/src/main.rs:26-27`). The MPL one builds KMS and DynamoDB clients and a `DynamoDbKeyStore` from request-chosen regions, table names and KMS ARNs, using the ambient credential chain (`mpl/test-server/src/handlers.rs:137-147`, `:425-430`). Any process on the host (TA9), or a container sharing the host network, could ask a running server to call KMS and DynamoDB with the developer's or CI job's credentials.
- Mitigation: loopback bind, `publish = false` in all four `Cargo.toml` files, and the servers are not part of the published crates. Whether a web page could reach them through a CORS pre-flight was not tested.
- Residual: out of the library's attack surface. Recorded so that nobody binds these elsewhere or runs them with production credentials.

## 9. Recommendations

From section 11 of the source threat model.

### 9.1 Configuration

- Prefer single-key `KmsKeyArn` or `KmsMrKeyArn` over Discovery and MRDiscovery. If Discovery is required, scope `kms:Decrypt` in IAM to the intended keys (TM-MPL-002, TM-MPL-007).
- Default to REQUIRE_ENCRYPT_REQUIRE_DECRYPT with commit-key suites (TM-MPL-006, TM-MPL-008).
- When sharing a cache, derive partition ids and logical names only from validated, NUL-free values. Keep the default random partition id unless sharing is intended. Never reuse a logical key store name across physical key stores (TM-MPL-009, TM-MPL-010).
- Set the ESDK `max_encrypted_data_keys` to a small number for any service that decrypts ciphertext from third parties, and set request timeouts (TM-MPL-025).
- Keep storm-tracking settings within the spec's ordering (Grace Interval <= Inflight TTL <= Grace Period, each at least 1 s), and keep the TTL much larger than the grace period (TM-MPL-018).
- Use bounded durations (TM-MPL-018, TM-MPL-023).
- Do not return MPL errors verbatim to the sender of a ciphertext, and escape provider info when logging (TM-MPL-003, TM-MPL-021).
- Run the test servers only on development hosts without production credentials (TM-MPL-026).

### 9.2 Implementation

- Reject `0x00` in partition id, logical key store name and branch key id at keyring build or resolve time, or raise a spec change to length-prefix the cache-id fields. Add a NUL regression test (TM-MPL-009, TM-MPL-010, BUG-06).
- Bound the per-message key-store work on decrypt: count distinct versions per call, cache negative results briefly, and give the whole decrypt a deadline. Add the two reproducers the source describes (TM-MPL-025).
- Clear the in-flight mark when a refresh fails, and give a fan-out-saturated waiter its own deadline (TM-MPL-018).
- Use `checked_add` for every `SystemTime + Duration`, bound durations in `build()`, and compute deadlines before taking the state lock so that no panic can poison it (BUG-01, TM-MPL-018).
- Restore the spec's storm-tracking constraints in `StormTrackingCmcBuilder::build` (TM-MPL-018).
- Require a cache that refreshes early to report its grace period, or warn when it returns `None` (TM-MPL-010).
- Rewrite the region only for `mrk-` ARNs in MRDiscovery (BUG-04, TM-MPL-007).
- Return an error instead of `.expect` on ECDSA keygen (BUG-05a).
- Truncate the output buffer on `aes_encrypt` `Err`, align the `aes_decrypt` guard with its callee, and fix its error text (BUG-07).
- Wipe the transient decrypt buffers listed under TM-MPL-015, wrap the private key `Vec` in `ecdsa_generate_keypair` in `Zeroizing`, and consider an active sweep of expired `LocalCmc` entries (TM-MPL-015).
- Add `mpl/.duvet/config.toml`, annotate the MPL MUSTs, and pin the spec revision (TM-MPL-019).
- Any future caching CMM must bind the commitment policy (or the suite) into its cache id (TM-MPL-008, TM-MPL-010).
- Shim: keep handles typed. Give `Keyring::adopt` a null check and a type tag, or use a generation-checked handle table instead of raw pointers. Document that raw-bridge callers must not free a handle while a call is running (TM-MPL-024).

### 9.3 Operational

- Rotate branch keys about yearly (TM-MPL-012), and alert if the ACTIVE record's version goes backwards (TM-MPL-005). Restrict DynamoDB write access to the key-store table (TM-MPL-005).
- Rotate a raw-AES wrapping key before about 2^32 wraps (TM-MPL-011).
- Scope KMS grants tightly (TM-MPL-002).
- Enable CloudTrail on the KMS keys and the DynamoDB table, and use the MPL user agent to attribute calls (TM-MPL-020).
- Never configure two physical key stores with the same logical name (spec, `#logical-key-store-name`).
- Monitor DynamoDB read throttling on the key-store table as a signal for TM-MPL-025.
