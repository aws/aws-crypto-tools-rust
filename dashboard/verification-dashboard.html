T01 Key-store records are read back with the same context that KMS checked Model proof, no failing check current

Rank 1, score 8.96, threat-driven. Related threats: TM-002 TM-005. Related bugs: none.

What part of the library this is
The branch key store. It saves branch keys as records in a DynamoDB table. AWS KMS protects each record's key and binds an encryption context (a set of labelled values) to it.
What could go wrong
A record could be swapped for another valid record, or the reader could trust labels that KMS never checked. This is threat TM-MPL-005, rated High. If the context used when reading differed from the one KMS checked, the reader would act on unchecked values.
What the proof checks
That three contexts are equal for a record: the one written with it, the one KMS checks when it unlocks it, and the one the reader rebuilds. It also checks that writing and reading back adds, drops or changes nothing, and that rotating to a new key version keeps this.
What the proof does NOT show
It does not show that KMS or DynamoDB behave as assumed. Both are modeled by assumptions (A_KMS, A_DDB). It does not cover replay of an older genuine record. A later edit to kms_ops.rs or branch_key_store.rs would not be detected.
Result
Verus reports 52 passing checks and 0 failing checks on a model of this code, not on the shipped code; KMS and DynamoDB are modeled by assumptions, so the KMS part is shown relative to those assumptions.

Findings and observations recorded in the docs

  • The two context builders are separate functions with no shared code. They agree today. An edit to one alone would break the match (observation O1, code reading).
Assumptions and hypotheses behind this proof (11)
  • A_KMS assumed: KMS binds the context given at write time and accepts a decrypt only for an equal context.
  • A_DDB assumed: DynamoDB returns exactly the attributes that were written.
  • A_NUM assumed: The hierarchy-version value is written as a canonical number.
  • A_NAME assumed: The reader and the writer use the same key store name.
  • A_ITER assumed: Walking through a map visits each key exactly once. This holds for the map type used (BTreeMap), but Verus cannot check it.
  • A_ARN assumed: The record lookup returns the record for the requested id and type. ARN resolution, grant tokens and other KMS errors are not modeled.
  • A_STR assumed: Strings behave as sequences of characters in the model. Byte and character splits agree because the relevant text is ASCII.
  • A_BLD assumed: The builder for branch key material behaves as the T02 model says.
  • H_WF premise: The written context has a table name and no enc entry. This is proved for every context the builders produce.
  • H_ENUM premise: The loops visit every entry of the maps. It can be satisfied.
  • H_SAME_EC code reading: One local context goes to both the KMS call and the stored record. A later edit that breaks this would not be detected.

Rank 4, score 6.40, capability-driven. Related threats: none cited in the targets docs. Related bugs: none.

What part of the library this is
The ECDSA signing code in the primitives crate (prim::ecdsa, function sign_fixed_len). It retries signing until it gets a signature of the required length.
What could go wrong
The loop could run without end, panic, or leave a half-written signature in the caller's buffer. The targets doc cites no threat for this target.

That the signing step is called at most 128 times. That on success the buffer holds exactly one whole signature of the required length. That on failure the buffer is unchanged. That a wrong-length buffer is rejected with no signing call.
What the proof does NOT show
It does not cover signature verification, key generation, a panic inside aws-lc-rs, timing, or the tiny chance that all 128 attempts fail. The signing step is abstract. Result

The branch key store, in the step that chooses which KMS key to call (resolve_key_store_arn). It covers the modes where the store is set to one single-Region key or one multi-Region key.

Someone who can write records in the database could name a different KMS key inside a record. The decrypt call would then go to a key they chose. This is threat TM-MPL-002 (a forged record).

That in both modes the KMS key used is always the configured one, never the one stored in the record. The record's key is accepted only if it is compatible: identical for a single-Region key, or the same multi-Region key in another Region. Otherwise the call fails with a validation error.
What the proof does NOT show
It does not cover the two discovery modes (see BUG-04 and T17). It does not show that KMS authenticates the record, and it does not cover replay of an older genuine record. It checks a model, not the shipped code.
Result

Glossary

Model-level proof
A proof about a hand-written copy of the code, written in a form Verus can read. The copy is called a model. Verus checks the logic of the model. A person checks that the model matches the code. Nothing checks that automatically, so an edit to the real code would not be noticed.
Shipped code
The Rust code in mpl/, prim/ and esdk/ as users get it. On this branch no proof checks it.
Verus
A tool that checks proofs written next to Rust code. It reports how many checks pass and how many fail.
Check (verification obligation)
One statement that Verus tries to prove. The line 'N verified, M errors' counts them. It does not count properties of the product.
Expected failure
A check that is written to fail on purpose. It states what the spec requires. The code does not meet it, so Verus rejects it. The failure is the finding. It is not a broken proof. Names in the proof files end in _FAILS or _EXPECTED_FAIL.
Assumption (A_ names)
A fact the proof takes as true without checking it. Example: KMS only decrypts when the context matches. If an assumption is wrong, the proof says nothing. Names starting with A_ (and A1, A3 and so on in one file) are assumptions.
Hypothesis (H_ names)
A condition about how the model relates to the code or how the code is used. A premise is a condition a theorem is stated under. A code-reading hypothesis is a fact a person checked by reading the code. Names starting with H_ are hypotheses. The page shows which kind each one is.
Honesty level
How strong the evidence for a target is: proved in the shipped code, partly proved in the shipped code on another branch (under 20 assumed aws-lc-rs facts), model proof, model proof with an intentional failing check, or no proof yet. A level is never shown as better than it is.
Stale result
A recorded proof result is stale when the proof file has changed since the run that produced it. A stale result must be re-run before it is trusted.
Target (T01 to T27, C01 to C08)
One thing the verification work proposes to prove. T targets come from the threat model. C targets come from a sweep of what the library can do. Retired targets are listed but not counted.
Score, rank, coverage gap, quick win
The score is severity x coverage gap x feasibility x blast radius, as recorded in the docs. The rank orders the targets by score. The coverage gap says how little existing tests cover the property. A quick win has a score above 6.0 and an effort of one week or less. This page copies these values and never recomputes them.
Threat (TM-MPL-nnn)
A threat from docs/mpl-threat-model.md. Each has a risk rating of Low, Medium or High. The threat model has 26 threats.
Bug (BUG-nn)
A bug report in docs/mpl-bug-reports/. Open means the code on main still has the problem. Fixed means it was fixed on main.
G1
A gap found in the spec review. The spec says a branch key record must have create-time and hierarchy-version. The code accepts a record without them.
Branch key
A key that protects other keys. The key store keeps branch keys as records in a DynamoDB table and uses AWS KMS to protect them.
KMS and DynamoDB
AWS KMS is the AWS service that creates and manages encryption keys. DynamoDB is the AWS database that holds key-store records.
Encryption context (EC)
A set of labelled text values that is bound to an encryption. Decryption works only if the same values are supplied again.
AAD
Additional authenticated data. Data that an encryption protects against change but does not hide. The encryption context is used as AAD.
Keyring and EDK
A keyring protects and recovers the data key for a message. An EDK (encrypted data key) is the protected copy of that key stored in the message.
CMM
Cryptographic materials manager. It decides which algorithm suite and keys are used and asks the keyrings to do the work.
Commitment policy
A setting that says whether messages must use algorithm suites that bind the ciphertext to one key. It guards against attacks where one ciphertext decrypts under two keys.
Cache identifier
A fingerprint (SHA-384 hash) used to look up cached branch keys. Two different keyring settings must never produce the same one.
NUL byte
The byte with value zero (0x00). The cache identifier uses it as a separator. A field that contains it can make two different settings look the same (BUG-06).
TTL and grace interval
TTL is how long a cache entry may be used. The grace interval is a wait before a second caller may refresh the same entry.
Panic
A Rust crash. The program stops the current work instead of returning an error.
Mutex and poisoned lock
A mutex is a lock that lets one thread use shared data at a time. If a thread panics while it holds the lock, the lock is marked poisoned and later users get an error.
Mahnush_Verus
Another branch of the repository that holds in-crate Verus proofs (VR-013, VR-014 for C03). Nothing from it is merged here.

Rules this page follows, and where the data comes from

  • Every number on this page is read from the repository docs or from a recorded Verus run. Nothing is typed in by hand.
  • A proof result is marked STALE when the proof file has changed since the run that produced the result.
  • No level is shown as an upgrade of a lower level. A model proof is never shown as a proof of the shipped code.
  • Scores, ranks, coverage gaps and quick wins are copied from docs/mpl-verification-targets.md. They are not recomputed and a proof does not change them.
  • A passing model proof does not mean a threat is handled. It means only what its card says it checks.
  • If a docs statement and a Verus run disagree, the page shows the disagreement and uses the weaker reading.
