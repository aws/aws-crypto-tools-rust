## New findings (all labeled static reasoning unless stated)
N1 Storm-tracking: a key left in flight by a leader that never `put`s (key store error, caller cancellation) is neither cleared by the error path nor by the same-key prune (`state_locked` keeps the caller's own key, storm_tracking.rs:249-258). After `in_flight_ttl` (default 10 s) a miss for that key returns `Throttling` on classification (`:322-323`), forever, until some other key's call prunes it or a `put` for it happens. Single-key, low-traffic encrypt-only deployments are exposed. Test `test_get_miss_inflight_exceeds_ttl_fails` (tests/test_storm_tracking_cmc.rs:761) encodes the error but not recovery. Spec ambiguity: "the time spent so far exceeds the Inflight TTL".
N2 Storm-tracking: waiter in the cache-miss, key-not-inflight, fan-out-saturated state has `deadline: None` (storm_tracking.rs:313) so `wait_for_leader` (`:360-398`) never times out by itself; it ends only when a slot frees (prune after `in_flight_ttl`, or a `put`). Spec FanOut: blocked "until the number of unique keys ... drops below this number, or until the amount of time that request has been outstanding exceeds the Inflight TTL".
N3 Availability amplification: on decrypt, an attacker who controls EDKs can use the public branch key id and arbitrary 16-byte versions (hierarchical_keyring.rs:752-763 filter only on provider id and bkid; version read at `:890-895`). Each distinct version is a cache miss, marks a key in flight, calls `get_branch_key_version` (DDB GetItem, `ResourceNotFound`), and never `put`s; no negative caching. Filling `fan_out` (20) in-flight slots stalls every other cache-miss lookup until entries age out (10 s). Cache hits are still served (storm_tracking.rs:274-280). ESDK `max_encrypted_data_keys` defaults to `None` (esdk/src/config.rs:34-42), so the EDK count per message is not capped by default.
N4 SharedCmm output checks do not re-check the request's commitment policy, requested suite equality, RECK superset, or PDK/EDK correspondence (cmm-interface.md "Get Encryption Materials" MUSTs). The built-in `DefaultCmm` does the first two (default_cmm.rs:97, :184). The ESDK re-checks the policy (esdk/src/materials.rs:130, :202). A user CMM called by another consumer of the MPL gets no such backstop.
N5 `GetEncryptionMaterialsInput::max_plaintext_length` is carried (cmm/types.rs:23, :66) but `DefaultCmm` never reads it.
N6 `cache_entry_within_limits` maps `duration_since` errors to zero elapsed (hierarchical_keyring.rs:989-996): a cache entry whose `creation_time` is in the future (backwards clock step, or a user cache) counts as fresh. Spec formula `now - creation <= ttl` allows it. Wall clock (`SystemTime`) is used for all TTL checks.
N7 Errors: `NoMatchingDataKey` carries `DataKeyInfo` (provider id + provider info, never ciphertext): `with_encrypted_data_keys` (error/generated.rs:1064), getter `:1591`, `DataKeyInfo` prim/src/error.rs:378. `Display` prints only provider ids (generated.rs:448-449); `Debug` prints the full provider info as text or hex (generated.rs:270-271, prim/src/error.rs:410-420). Provider info can be a KMS key ARN (account id) or branch key id, and comes from attacker-controlled message bytes, so it is a log-content concern.
N8 `Error::from_sdk` is public (error.rs, `from_sdk`) so custom keyrings classify SDK errors the same way; the classifier maps code strings to kinds (error.rs THROTTLING_CODES etc.).
N9 Four test-server crates exist (`mpl/test-server`, `prim/test-server`, `esdk/test-server`, `esdk/shims/aws-esdk-cpp/test-server`). All bind `127.0.0.1` only (src/main.rs:26 in each; prim :23) and have no authentication. The MPL one creates keyrings from request bytes, including a raw wrapping key (handlers.rs:64-69), and keeps registries in `HashMap` behind `Mutex` with `.expect` on lock (handlers.rs:73). Its README (4 operations) is stale vs `wire.rs:60-83`. It also contains the in-repo implementations of `Keyring` (`StaticKeyring`, handlers.rs:470-495) and `BranchKeyIdSupplier` (handlers.rs:441-460): the first returns materials unrelated to its input, so the transition checks apply to it.
N10 C++ shim #188 (41f1d51): `ddb_client` now sets the caller's retry config on the DynamoDB client config (shim lib.rs:1411-1419) because the DDB client ignores the `SdkConfig` retry config; before, caller retry settings did not reach DDB calls (CreateKey/VersionKey `TransactWriteItems` and `GetItem`). Behavioral, no new trust boundary. #189 (5f2dc72): current files link only the archive by path (`CMakeLists.txt:39-53`, `Makefile:4-12`, `performance-tests/Makefile:10-13`) and `build.rs:7-11` compiles the cxx runtime into the staticlib; the test-server build script links the prebuilt cdylib with an rpath to the shim's own `target` dir (`test-server/build.rs:44-49`). Diff itself not read.
N11 Spec silent / ambiguous: exact KBKDF fixed-info layout (hierarchical keyring "Branch Key Wrapping" gives only salt, key, label; code uses `label || 0x00 || salt || 0x00000100`, branch_key_wrap.rs:122-143), spec internal default conflict in storm tracking (default Inflight TTL 20 s vs default Grace Period 10 s violates its own MUST; code uses 10 s), whether OnDecrypt "configured Branch Key Identifier" means the supplier's result, and who clears a stale in-flight mark.
